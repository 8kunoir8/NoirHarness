# M2.0 Native Engine — Design

**Date:** 2026-11-11
**Status:** Approved design; implementation plan not written
**Milestone:** M2.0
**Depends on:** M1.5 (current `main`, merge `114009e`)

## 1. Intent

Add a second engine implementation that owns the agent loop. The native engine talks the OpenAI-compatible chat-completions protocol directly, assembles tool calls, executes built-in tools through kernel services, and emits the same normalized events as the ACP engine. ACP remains the default and keeps working for every provider kind. A model can opt into `engine: "native"` only when its provider is `openai-completions`.

Success means: with a local OpenAI-compatible fake server, a native session streams a reply, runs `fs.read`, asks for `shell.exec` approval, executes it, streams the follow-up, and replays to the same projections after a kernel restart — with no ACP process involved.

## 2. Correction carried into this spec

The milestone table and §7.1 sketch an `AgentEngine` interface that does not exist in code. The implemented seam is `packages/engines/acp/src/index.ts`: `AcpClient`, `AcpSession`, `EngineUpdate`, `EnginePermissionRequest`, `EnginePromptResult`, `PermissionDecision`, consumed by `packages/kernel/src/engineManager.ts`. This milestone extracts that contract into a shared package and makes the spec's §7.1 match the code. ACP behavior must not change during extraction.

## 3. Scope

### In scope

- `packages/engines/core`: neutral `Engine`/`EngineSession` contract and shared update types.
- `packages/engines/native`: OpenAI-compatible streaming client, turn loop, tool assembly and execution, history reconstruction.
- Engine selection per model (`acp` default, `native` opt-in), enforced at session creation.
- Built-in tools: `fs.read`, `fs.list`, `fs.search`, `fs.write`, `fs.replace`, `fs.delete`, `shell.exec`, `skill.list`, `skill.read`.
- Approvals through the existing `permission.requested` / `approval.respond` path.
- Usage accounting, interruption, turn timeout, replay-safe events.
- Conformance scenarios shared by ACP and native.

### Out of scope

- Anthropic Messages, Google Generative AI, and OAuth providers for the native engine.
- Subagents, steering, web/network tools, MCP, plan/todo UI generation.
- Sandboxed shell execution (approval-gated only).
- LSP, PTY, and the tool broker.
- Removing ACP.
- Per-agent skill filtering (M2.2 owns profiles; this engine loads the enabled skill set like ACP).

## 4. Architecture

```
packages/engines/core     Engine, EngineSession, EngineUpdate, EnginePermissionRequest,
                          EnginePromptResult, PermissionDecision, EngineCapabilities
packages/engines/acp      AcpClient implements Engine (adapter over current code)
packages/engines/native   NativeEngine implements Engine
packages/kernel           EngineManager selects an Engine by session.engine
```

### 4.1 Contract (`packages/engines/core`)

Moved verbatim from ACP where possible, so ACP imports do not change semantically:

```ts

  | { role: "user"; text: string }

```

export interface EngineSession {
  prompt(
    content: Array<{ type: "text"; text: string }>,
    handlers: {
      onUpdate(update: EngineUpdate): void;
      onPermission(request: EnginePermissionRequest): Promise<PermissionDecision>;
      onSkillRead(name: string): void;
    },
  ): Promise<EnginePromptResult>;
  interrupt(): Promise<void>;

  readonly pid?: number;
  setModel?(model: EngineStartOptions["model"]): Promise<void>;

  id: "acp" | "native";

```

- `onSkillRead` is new and additive: ACP may ignore it; native calls it after `skill.read` succeeds so `EngineManager` can emit `skill.loaded` from the existing `skillIndex`.
- `EngineStartOptions.history` is empty for ACP (it keeps its own session state) and reconstructed for native.
- `EngineManager` keeps ownership of turns, approvals, commands, usage projection, and status. Engines only produce updates.

Capabilities: ACP `{streaming: true, tools: true, diffs: true, approvals: true, subagents: true, steering: true, modelSelection: true}`; native `{streaming: true, tools: true, diffs: true, approvals: true, subagents: false, steering: false, modelSelection: true}`.

### 4.2 Engine selection

Migration 5:

```sql
ALTER TABLE models ADD COLUMN engine TEXT NOT NULL DEFAULT 'acp';
CREATE INDEX idx_models_engine ON models(engine);
```

- `ModelCreateParams` gains `engine: z.enum(["acp", "native"]).default("acp")`.
- New RPC `model.setEngine({ id, engine })`. It rejects `native` unless the model's provider `api_kind = 'openai-completions'` with `RpcFault(conflict, "Native engine supports openai-completions providers only")`.
- `models.engine` is included in `ModelView`.
- `SessionService.create(workspaceId, { modelId?, agentId? })` resolves the engine from the chosen model (`models.engine`), defaulting to `acp` when no model exists. It stores `sessions.engine` and `sessions.config_snapshot_json = { engine, modelId, agentId }`.
- A session's engine is fixed at creation. `session.setModel` rejects a model whose `engine` differs from `sessions.engine` with `RpcFault(conflict, "Model engine differs from the session engine")`; switching engines requires a new session.
- `EngineManager.ensureEngine` builds the engine through a registry keyed by `sessions.engine`; unknown engine ids fail the turn with `turn.failed`.

## 5. Native turn loop

One turn:

1. Build the request from history plus the new prompt text and the system message.
2. `POST {baseUrl}/chat/completions` with `stream: true`, `stream_options: { include_usage: true }`, `tools`, `tool_choice: "auto"`.
3. Read SSE; validate each `data:` JSON against an internal zod schema; ignore comment lines and `[DONE]`.
4. Emit assistant text as `message.delta` (via `EngineUpdate.message`, one synthetic message id per turn).
5. Assemble streamed `tool_calls` by index: `id`, `function.name`, concatenated `function.arguments`.
6. On finish, append the assistant message to history. For each tool call:
   - validate arguments against the tool schema; a schema failure is a tool result with `status: "failed"` and a readable message, not a failed turn;
   - call `onPermission` when the tool requires approval; `reject*` returns a tool result `"Permission denied by the user"`;
   - execute, emit `tool.updated` with `in_progress`/`completed`/`failed`, append the result message.
7. Repeat from 2 while there were tool calls and the turn is not interrupted; otherwise return `{stopReason: finish_reason ?? "stop", timedOut: false}`.
8. On `interrupt()`: abort the fetch, cancel the running tool (shell kill tree), return `{stopReason: "cancelled", timedOut: false}`. `EngineManager` marks the open message interrupted.
9. On timeout: abort, kill tools, return `{stopReason: "timeout", timedOut: true}`.

Limits: at most 24 model requests per turn; exceeding it fails the turn with "Tool loop limit reached". Default `turnTimeoutMs` is 120,000, matching ACP.

System message content is fixed and short: identity, workspace root, tool names with one-line descriptions, and the enabled skill names. It contains no secrets.

## 6. Transport

- `fetch` with `AbortSignal`; no SDK.
- Request body is `application/json`; authorization is `Bearer <key>` read from the vault for that turn only.
- SSE parser handles: arbitrary chunk boundaries, `\r\n`, multiple `data:` lines per event, comments, blank-line event termination, and `[DONE]`.
- Malformed JSON or a schema mismatch terminates the turn with `turn.failed` message `Native engine returned an invalid stream chunk`; the raw chunk is not logged.
- HTTP non-2xx: read at most 8 KiB of the body, redact it through the call-site redactor, and fail with `HTTP <status>: <body>`; 401/403 produce "Check the provider API key".
- Redirects are not followed (`redirect: "error"`) so the key never reaches another origin.
- Base URL normalization strips trailing `/`; the path is always `/chat/completions`.

## 7. Tools and permissions

All paths resolve through the workspace root and the existing path guard; a path outside the workspace is rejected unless the tool is `fs.write`/`fs.replace`/`fs.delete` and the approval flow explicitly allows it. Tools are zod-validated before execution.

| Tool | Arguments | Approval | Result |
|---|---|---|---|
| `fs.read` | `{ path, offset?, limit? }` | none | UTF-8 text, 64 KiB cap |
| `fs.list` | `{ path?, depth? }` | none | names/kinds/sizes, 2,000 entries |
| `fs.search` | `{ query, path?, glob? }` | none | up to 200 matches `{path, line, text}`; literal by default, `regex: true` opt-in with a 200-char pattern cap |
| `fs.write` | `{ path, content }` | `write-outside-workspace` (always, in M2.0) | `{ bytes }` |
| `fs.replace` | `{ path, find, newText }` | same as write | `{ replacements: 1 }`; fails unless `find` matches exactly once |
| `fs.delete` | `{ path }` | `delete` | `{ deleted: true }`; files only, empty directories refused in M2.0 |
| `shell.exec` | `{ command, timeoutMs? }` | `shell` | stdout+stderr, 64 KiB cap, exit code; 120 s max |
| `skill.list` | `{}` | none | enabled skills `{name, scope, description}` |
| `skill.read` | `{ name }` | none | `SKILL.md` content, 64 KiB cap; calls `onSkillRead(name)` |

Rules:

- `shell.exec` runs with `cwd` = workspace root, `shell: true`, inherits `process.env`, and is killed as a tree on timeout/interrupt. It never runs when approval is rejected.
- M2.0 has no permission-policy enforcement (that arrives with M2.2), so `fs.write`, `fs.replace`, `fs.delete`, and `shell.exec` always ask. The category is `write-outside-workspace` for writes/replaces (matching `permissionCategory`), `delete` for deletes, and `shell` for commands. M2.2 may auto-resolve `allow`/`reject`, except outside-workspace writes, which always ask.
- Every tool result is truncated with an explicit `[truncated]` suffix and never includes a secret from the environment; the call-site redactor runs on outputs before they enter history.
- Tool calls emit `tool.started` with `toolKind` one of `read`, `write`, `shell`, `search`, `skill`, `other` so the office view can animate; `rawInput` is the validated arguments object.
- `command.started`/`command.output`/`command.completed` are emitted by `EngineManager` from `shell.exec`, matching ACP.

## 8. History and replay

- Native keeps history in memory per session: system message, user messages, assistant text/tool-calls, tool results.
- User prompts are persisted by the kernel. Today `EngineManager.prompt` only inserts a `turns` row and the renderer appends the bubble locally, so replay drops every user message; M2.0 makes `prompt` emit `message.delta { messageId: requestId, role: "user", block: { type: "text", text } }` immediately after the turns row, plus `message.completed { status: "done" }` for the same id. The renderer treats an already-rendered optimistic user message as a no-op.
- On a new session state (first prompt after boot or after `error`), history is reconstructed from the event log, newest-last:
  - `message.delta` role `user` → one user message per turn (blocks joined by `\n`);
  - `message.delta` role `assistant` text → assistant content;
  - `tool.started` + `tool.output`/`tool.completed`/`tool.failed` → an assistant tool call and a tool result;
  - `skill.loaded` adds no message.
- Reconstruction stops when the estimated token count (characters / 4) exceeds `contextWindow - maxTokens - 2,000`, dropping the oldest complete turns first. A trimmed history is logged as `engine.raw { engine: "native", payload: { trimmedTurns } }` (not shown in UI).
- Replay correctness: the persisted event stream alone must reproduce the chat projection; native never writes state that is not an event.

Usage:

- Prefer `usage` from the final chunk (`prompt_tokens`, `completion_tokens`).
- Without usage, estimate `inputTokens = ceil(chars/4)` and `outputTokens = ceil(chars/4)` and mark the turn via `usage.updated` with the estimate; cost is `0`.
- Context meter uses `prompt_tokens` of the last request as `contextUsed`; `contextWindow` comes from the model.

## 9. Protocol changes

- `PayloadSchemas["tool.started"]` gains optional `kind: z.enum(["read","write","shell","search","skill","other"]).optional()`.
- No other event changes. `permission.auto` is M2.2, not this milestone.
- `ModelView.engine`, `SessionView.engine` already exists in `SessionView`.
- New RPC `model.setEngine`; `model.create` accepts `engine`.

## 10. Security

- API keys stay in the vault and the request header; they are never written to events or logs. The M1.5 redactor remains the ingest boundary.
- Errors from provider responses are redacted before becoming `turn.failed` text.
- Tool arguments and results are untrusted. Shell output is truncated; file reads never bypass the workspace guard; symlinks are resolved before the guard.
- `shell.exec` is not sandboxed in M2.0. The permission defaults (`ask`) and agent policy are the only controls; this is recorded as a standing risk.
- `fs.search` compiles user-provided regex with a length cap and runs it per file with a per-file size cap; no catastrophic-backtracking mitigation beyond the 200-char pattern cap and the file cap. Documented as a known limitation.

## 11. Testing and acceptance

Unit:

- SSE parser: split chunks, multi-line data, CRLF, comments, `[DONE]`, malformed JSON.
- Tool-call assembly across deltas, multiple calls, argument fragments.
- History reconstruction from a fixture event list, including trim.
- One prompt appends exactly one `user` `message.delta`, and replay renders exactly one user bubble for it.
- Usage fallback and context calculation.
- Every tool's zod schema and path guard (outside workspace, symlink escape).
- `model.setEngine` rejects native for non-OpenAI providers; session creation stores the engine; `session.setModel` rejects an engine mismatch.

Integration (fake OpenAI server, mirroring the fake ACP server):

- Full native turn: stream, read a file, ask for `shell.exec`, approve, execute, follow-up reply.
- Reject: shell tool result is a denial, turn completes with no command.
- Interrupt mid-stream: turn completes as interrupted; no dangling fetch.
- Timeout: `timedOut` true and the command tree is killed.
- Two consecutive turns keep history and usage.
- Restart: prompt after kernel restart reconstructs history and succeeds.
- ACP conformance suite runs unchanged; native runs the same observable scenarios.

E2E (Playwright Electron):

- Configure a native model against the fake server; prompt; see a streamed reply; approve a shell tool; see the command card; restart the app; the transcript replays.

Acceptance:

1. `pnpm -r typecheck` and `pnpm -r test` pass; the ACP suite is unchanged.
2. A native session completes the full tool loop against the fake server with the same event types as ACP.
3. `model.setEngine` cannot create an unusable model/provider combination.
4. Killing the kernel mid-native-turn and restarting leaves the session recoverable and promptable.
5. No provider key appears in events, approvals, or logs.

## 12. Risks

| Risk | Mitigation |
|---|---|
| OpenAI-compatible servers differ in streaming/tool formats | Zod at ingest; one documented dialect; fake server covers the strict variant |
| ACP refactor regresses M1 behavior | Mechanical extraction; full existing ACP suite unchanged and green |
| History reconstruction drifts from live history | Same builder used for reconstruction and live appends; replay test |
| Tool output bloats events | 64 KiB caps and explicit truncation |
| Unsandboxed shell | Default-ask policy, no auto-allow from this milestone, documented risk |
| Context overflow | Trim oldest complete turns; surface the model's context window |

## 13. Open questions resolved

- Engine relation: coexist, selectable per model, ACP default.
- Capability scope: minimal coding loop plus skills; no subagents/web/MCP.
- Providers: OpenAI-compatible only.
- Transport: hand-rolled fetch + SSE.
- Shell: approval-gated, unsandboxed.
