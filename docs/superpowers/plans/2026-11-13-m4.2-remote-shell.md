# M4.2 Remote Shell Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A paired browser on the LAN runs the same harness against the same kernel, with a pairing code from the desktop app, a revocable device cookie, and no TLS — trusted network only.

**Architecture:** `rpcServer.ts` is split into a reusable listener factory so one kernel can hold two: the loopback listener from M4.1 (token auth, unchanged) and a LAN listener that exists only after `remote.enable` (cookie auth, host/origin checks, static assets, `/pair/redeem`). Devices are rows in the kernel DB keyed by a hash of the cookie secret. The renderer learns its transport from `transport.ts`: preload when it has one, same origin when it does not.

**Tech Stack:** Node 24, TypeScript strict ESM, `ws`, `node:http`, `node:crypto`, `node:fs`, `node:os`, React, vitest, Playwright Chromium.

**Spec:** `docs/superpowers/specs/2026-11-13-m4.2-remote-shell-design.md`

## Global Constraints

- Node >= 24, pnpm >= 10, TypeScript strict (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`), ESM with `.js` import extensions, zero new runtime npm dependencies.
- One commit per task on `main`; never branch, never push, never amend.
- Service-boundary failures are `RpcFault(ErrorCodes.<code>, msg)`; HTTP routes answer JSON with an explicit status.
- Static string-keyed lookups are `Record<string, true>`, never `Set`.
- Never `: any` / `as any`; prefer `Promise.withResolvers()`.
- Never log a token, a pairing code, a prompt, or file contents.
- Targeted suites per task; one full gate at the end against the 893 unit / 16 e2e baseline.
- `apps/desktop` renderer tests: jsdom, `include: ["test/**/*.test.{ts,tsx}"]`, no jest-dom matchers.

## Review Focus

- **Token in a URL.** The browser must never carry a credential in the query string or a header; the cookie is the only browser credential and it is `HttpOnly`. Task 2.
- **DNS rebinding.** Host must resolve to this machine's own names, Origin must equal Host. Task 3.
- **Revocation is immediate.** A revoked device's open sockets close; it is not merely denied at the next handshake. Task 4.
- **Path traversal.** `NOIR_WEB_ROOT` serving must not read outside the root, under any encoding. Task 5.
- **Admin verbs.** `remote.*` over a device cookie is a whole class of escalation; loopback-only, enforced in one place. Task 6.
- **The desktop must not change.** Loopback behaviour, the Electron window, and the four `api.ts` mocks stay byte-compatible. Task 7.

### Task 3: LAN listener with host/origin checks and pairing endpoint

**Files:**
- Create: `packages/kernel/src/remoteAccess.ts`
- Test: `packages/kernel/test/remoteAccess.test.ts`

**Change:** `RemoteAccess` owns the optional listener: `enable()` binds `0.0.0.0:0`, `disable()` closes it, `status()` reports `{enabled, port, url?}`. Per-connection guard: `Host` in `{localhost, 127.0.0.1, [::1], <interface IPv4s>}` else `421`; `Origin`, when present, must equal `http://<host>` else `403`; `/health` and `/shutdown` are `404` here. `POST /pair/redeem` with the code rules from the spec (10 min, single use, 5 attempts per code, 5 per IP per minute → `429`).

**Verification:** `pnpm exec vitest run test/remoteAccess.test.ts` — host mismatch 421, foreign origin 403, `/health` 404, redeem success sets the cookie, second redeem 401, expiry 401, 6th attempt 429, `/pair/redeem` body cap 1 KiB.
