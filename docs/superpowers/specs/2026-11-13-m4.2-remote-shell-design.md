# M4.2 — Remote shell over a paired LAN

Status: design. Supersedes nothing; extends `2026-11-13-m4.1-daemon-design.md`, which deliberately
left remote access, TLS and mobile out of scope.

## 1. Intent

The daemon already outlives the window and owns every piece of state. This milestone makes that
kettle useful: **open the same harness in a browser on the same network, after pairing once from the
desktop app.**

What a user does:

1. Desktop → Settings → *Devices* → *Allow devices on this network* → the kernel starts a second
   listener and shows a one-time URL.
2. Open the URL on a phone or another machine → the token in the fragment is exchanged for a cookie
   → the full harness loads, same UI, same sessions, same approvals.
3. Any device is listed and revocable from the same pane; revoking kills its sockets immediately.

What this is not: not TLS, not a relay, not a hosted service, not a mobile layout, not multi-user.
The trust model is **the LAN is trusted** — see §9 of the base design and §10 here.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Listener model | Two listeners in one process: loopback (always, token auth, unchanged) and LAN (opt-in, cookie auth) | No daemon restart when remote access is toggled, no silent wide bind at every launch, and the loopback surface stays byte-identical to M4.1 |
| Where the setting lives | Kernel DB (`settings['remoteAccess']`), read/written through RPC | It is kernel state, like every other setting; the app never parses the DB |
| Browser credential | `HttpOnly` cookie `noir_device=<id>.<secret>`; no token in a URL or header | A browser cannot set headers on a WebSocket, and a query token lands in logs and history |
| At rest | `sha256(secret)` only; id is opaque | A copied DB does not yield a usable device |
| Admin boundary | `remote.*` methods and `/pair/start` are **loopback-only** | A stolen device cookie cannot mint or revoke devices; losing a laptop does not hand over the enrolment authority |
| Binding | LAN listener binds `0.0.0.0`; the URL advertises the first non-internal IPv4 | One network, one address; IPv6 on a LAN is a non-goal for this milestone |
| Web assets | Served by the kernel from `NOIR_WEB_ROOT` when set; only on the LAN listener | The Electron window keeps loading `file://` as it does today |
| Both listeners share | `handlers`, `broadcast`, the client set for presence | One session list, one event stream; a device and the desktop see the same runs |

## 3. Listener and transport

`startRpcServer` is split so it can run twice:

```ts
createRpcListener({ handlers, broadcast, authorize, buildId?, requestShutdown?, onStopped? })
```

- `authorize(req)` decides a connection: the loopback listener keeps the M4.1 rule (runtime token
  via `?token=` or `Authorization: Bearer` for `/shutdown`); the LAN listener requires the device
  cookie **and** an origin/host match (§6).
- Each listener has its own `http.Server` and `WebSocketServer`, but events broadcast to the union of
  clients, so a subscription opened by a device and one opened by the desktop are peers.

The remote listener is created by `remoteAccess.enable()` and destroyed by `disable()`; it does not
exist otherwise. `RuntimeInfo` gains an optional `remotePort` so tooling can find it; the token is
never written there for the remote port.

### HTTP surface on the LAN listener

| Route | Auth | Behaviour |
|---|---|---|
| `GET /` and any non-API path | none | static asset from `NOIR_WEB_ROOT`, SPA fallback to `index.html` |
| `POST /pair/redeem` | none (rate-limited) | `{code}` → `Set-Cookie` + `{ok:true}`, or `401`, or `429` |
| everything else | cookie | `404 {error:"not found"}` |

`/health` and `/shutdown` are **not** served on the LAN listener: health leaks the pid to the network
and shutdown has no business being reachable from a browser.

## 4. Pairing

- `remote.pair` (loopback only) creates a code: 24 random bytes, base64url (32 chars), TTL **10
  minutes**, **single use**, and answers `{url, code, expiresAt}` where
  `url = http://<lan-ip>:<remotePort>/pair#<code>`.
- The code is in the **fragment**, so it never reaches the kernel's own access log, any proxy, or the
  browser's `Referer`.
- `POST /pair/redeem {code}`:
  - constant-time compare against the live code; wrong code → `401 {ok:false}`;
  - 5 wrong attempts on a code burns it (the pane shows *expired* and offers a new one);
  - at most 5 attempts per IP per minute → `429`;
  - success mints a device row, returns `Set-Cookie: noir_device=…; HttpOnly; SameSite=Strict; Path=/;
    Max-Age=2592000` and `{ok:true, deviceId}`; the code is consumed.
- The pane shows the URL, the countdown, and the new row, labelled from the user agent (*iPhone*,
  *Windows PC*, *Browser*) so the list is readable without a rename affordance.

## 5. Devices

```sql
CREATE TABLE devices (
  id TEXT PRIMARY KEY,
  label TEXT NOT NULL,
  token_hash TEXT NOT NULL UNIQUE,
  created_at INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL,
  revoked_at INTEGER
);
```

`remote.devices` lists `{id,label,createdAt,lastSeenAt,revokedAt,connected}` (`connected` = it holds a
live socket right now). `remote.revoke {id}` marks it revoked **and closes its sockets**, so
revocation is not "will not re-authenticate" but "is gone now". `last_seen_at` is bumped at most once
a minute per device to keep writes out of the hot path.

## 6. Origin and Host checks

Both are enforced on the LAN listener before anything else happens:

- **Host** must name this machine: `localhost`, `127.0.0.1`, `[::1]`, or one of the interface IPv4
  addresses from `os.networkInterfaces()`. Anything else → `421 Misdirected Request`. This is what
  stops DNS rebinding: a page on `evil.example` that resolves to `192.168.1.20` still sends
  `Host: evil.example`.
- **Origin**, when present, must equal `http://<Host header>`; a request with a foreign `Origin` →
  `403`. A browser cannot forge either header, so the pair together stop a cross-site page from
  driving the socket. Non-browser clients (curl, tests) send no `Origin` and are unaffected.
- The cookie is `SameSite=Strict`, so a cross-site navigation does not carry it at all.

## 7. Browser client

`apps/desktop/src/renderer/api.ts` stops assuming the preload bridge. A new
`renderer/transport.ts` resolves one of two modes:

```ts
type Transport = { kind: "desktop"; url: string } | { kind: "browser"; url: string };
```

- *desktop*: `window.noir.kernelInfo()` → `ws://127.0.0.1:<port>/?token=…` (unchanged).
- *browser*: no preload → `ws://<location.host>/` with no token; the cookie rides the upgrade. A
  refused handshake cannot be inspected by script — the browser reports it as a bare `error` event —
  so a connection failure in browser mode renders *this device is not paired* rather than echoing a
  generic socket error. The pairing link itself comes from the desktop pane; there is nothing the
  page could usefully offer to click.

The two remaining preload methods get browser shims in the same module: `openExternal` →
`window.open(url, "_blank", "noopener,noreferrer")`; `automationsArmed` → nothing (no tray).

`/pair` is a renderer route: reads the fragment, `POST`s it, `location.replace("/")` on success. The
fragment is cleared from the address bar first.

## 8. What a remote client may call

The paired device gets the **same handler map** as the desktop — it is the same UI, and a reduced map
would produce a UI that silently lies about what it can do. The boundary is not the method list but
the admin verbs, which are loopback-only:

```ts
const loopbackOnly: Record<string, true> = {
  "remote.enable": true, "remote.disable": true, "remote.pair": true,
  "remote.devices": true, "remote.revoke": true,
};
```

A non-loopback caller receives `RpcFault(ErrorCodes.forbidden, …)`. Every other method — including
`fs.write`, `provider.create`, `schedule.*` — behaves exactly as it does for the desktop, because the
pairing step is the authorisation event. This is stated here so nobody later "improves" the ACL into
something that breaks the UI.

## 9. Static serving

- Only when `NOIR_WEB_ROOT` is set (the app passes `<dist/renderer>` at spawn).
- `GET`/`HEAD` only; anything else `405`.
- Resolution: `resolve(root, "." + pathname)` must stay under `root` (prefix check after `resolve`),
  and the path must not contain `..` or a null byte → `404`.
- An unknown path with an extension → `404`; without one → `index.html` (SPA routes).
- `index.html`: `cache-control: no-store`. Everything else: `immutable, max-age=31536000` — Vite
  content-hashes the filenames.
- MIME by extension with a fixed table (`.js`, `.css`, `.html`, `.svg`, `.png`, `.woff2`, `.json`,
  `.map`, `.ico`); unknown → `application/octet-stream`.

## 10. Security model, restated

Trusted network only. **No TLS**: the cookie crosses the LAN in cleartext and an on-path attacker can
steal it and impersonate the device until it is revoked. That is an accepted property of pairing on a
LAN, not an oversight, and the pane says so in one sentence. If the network is hostile, do not turn
this on. Revocation, the loopback-only admin boundary, `SameSite=Strict` and the host/origin checks
are what limit the blast radius; they do not make an untrusted network safe.

## 11. Failure modes

| Situation | Behaviour |
|---|---|
| No `NOIR_WEB_ROOT` | LAN listener still serves `/pair/redeem`; `/` answers `404` with a one-line hint. Pairing a device that cannot load the UI is a configuration error, not a silent one. |
| `0.0.0.0` unavailable (firewall/OS) | `enable()` rejects with `RpcFault(internal, "cannot bind 0.0.0.0: <code>")`; the toggle returns to off. |
| No non-internal IPv4 | `remote.pair` answers `409` with *no network address*; the toggle stays on, the URL is not invented. |
| Kernel restarts | Devices and the setting persist; the listener starts with the kernel, so a paired browser reconnects on its own. |
| Port changes | `remote.status` reports the current `remotePort`; the pane shows the current URL rather than a stale one. |
| Cookie present but device revoked | Upgrade `401`; the client shows the *not paired* state. |

## 12. Non-goals

TLS and certificate pinning; tunnels or relays; a mobile-specific layout; multi-user or per-device
permissions; remote code execution surfaces beyond the existing tool broker; serving the desktop UI
over the loopback listener (Electron keeps `file://`).

## 13. Testing

- **Kernel unit** (`remoteAccess.test.ts`): pairing single-use, expiry, burn after 5 failures, IP rate
  limit, cookie round-trip, revoke closes the socket, host/origin rejection (421/403), traversal
  (`../`, encoded, absolute), SPA fallback, MIME table, loopback-only admin verbs.
- **Renderer unit**: transport resolution in both modes; the `/pair` route posts once and replaces the
  location.
- **E2E** (`remote.spec.ts`): enable remote access through RPC, pair with `fetch` + cookie jar, load
  `/` in Playwright's Chromium against the LAN listener, see the harness boot over the socket, then
  revoke and watch the page drop to the unpaired state. Runs headless with no Electron window.
- Existing suites must stay green: the loopback listener is unchanged, and the renderer's desktop mode
  is byte-identical in behaviour.

## 14. Compatibility

No changes to existing tables; migration 10 adds `devices` only. Existing runtimes start with remote
access off, exactly as M4.1 left them. A device paired by this build stays valid across kernel
restarts and app updates (the hash is in the kernel DB, not the app).
