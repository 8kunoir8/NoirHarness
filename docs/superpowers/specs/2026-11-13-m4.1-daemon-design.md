# M4.1 Daemon Design Specification

- Date: 2026-11-13
- Status: approved design, implementation not started.
- Scope: the second half of M4 — the kernel outlives the window.

## 1. Intent

M4.0 made a schedule fire "without anyone present", but not without anyone *running*: the kernel is a
child of Electron main (`apps/desktop/src/main.ts`), `before-quit` kills it, and
`window-all-closed` quits the app. Close the window and nothing fires. The base design already named
the gap: "M4 automation + remote runtime," and M4.0's own spec deferred it — "No daemon. … making it
survive a quit is a service install and a persistent trust surface, which belongs with remote
runtime."

This is that piece, without the remote: the kernel becomes a local daemon that the app attaches to,
so a scheduled run happens with no window open, and a turn already in flight survives the window
closing.

Success:

- Launching the app attaches to a running daemon; launching with none spawns one. Either way the UI
  reaches a kernel with no extra step.
- Quitting the app leaves the daemon running; automations keep firing; relaunching reattaches to the
  same pid and the same database.
- The daemon is still reachable only on `127.0.0.1` with the per-start token, and still refuses a
  second instance over the same data directory.
- An app update never talks to the previous build silently: an idle daemon is replaced, a busy one
  is a question the user answers.
- One action stops it, and it is discoverable while no window is open.

Non-goals:

- **No remote or mobile access.** No bind beyond loopback, no TLS, no origin policy for browsers.
  Attach is same-machine only.
- **No OS service.** No SCM, launchd, or systemd unit, and no elevation; a service install is an
  installer project with its own identity and permissions story.
- **No start-at-login.** The daemon begins with the first app launch after a reboot; a scheduled run
  missed while the machine was off is already recorded as `missed` by M4.0's catch-up.
- **No supervisor.** If the daemon dies while the app is closed, nothing restarts it before the next
  launch. A respawning parent buys crash recovery at the cost of a second process, a second log, and
  a second failure mode; the record of what was missed is the honest signal.
- **No protocol change.** JSON-RPC schemas and the event stream are untouched. The new surface is
  HTTP, outside the data plane.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Ownership | App spawns a **detached** kernel, else attaches | Reuses the runtime file, the lock, and the pid+health claim that already exist; no new discovery mechanism |
| Quit semantics | Quit leaves the daemon; `Quit and stop daemon` stops it | The whole point: a scheduler that stops at quit cannot fire while you are away |
| Window close | Hides to the tray, does not quit | A tray that vanishes when the window closes is not a stop control |
| "Different build" | `buildId` = sha256 of the kernel entry file | Exact, needs no release plumbing, and is true in dev and packaged builds alike |
| Liveness | `GET /health` on the existing HTTP listener | One handler on a server that already exists; no token needed because it carries no secrets |
| Version mismatch, idle | Stop, wait for exit, spawn | Silent because nothing is lost |
| Version mismatch, busy | Dialog: stop and restart, or keep the old build | A background automation must not be killed by an app update without a decision |
| Stop control | `POST /shutdown` with the runtime token | Lifecycle belongs on the control plane; JSON-RPC stays the data plane |
| Stale daemon that predates this change | `SIGTERM` to the recorded pid | It has no `/health` and no `/shutdown`; the pid is in the runtime file |
| Log | `<dataDir>/logs/kernel.log`, rotated at spawn | A headless process with `stdio: ignore` leaves no trace of why it died |
| Second app instance | `app.requestSingleInstanceLock()` | Two trays and two spawn races are both wrong |

## 3. Process lifecycle

Launch, in `apps/desktop/src/main.ts` by way of a new `src/kernelHost.ts`:

1. Read `<dataDir>/runtime/kernel.json`. Absent, or its pid is dead → **spawn**.
2. `GET http://127.0.0.1:<port>/health` with a 750 ms deadline. The reply must carry the same `pid`
   as the runtime file, else the recorded endpoint is stale → **spawn**.
3. Compare `buildId` with the hash of the kernel entry this app would spawn:
   - equal → **attach**;
   - different → **replace**, per §5.

Spawn:

```ts
spawn(nodeBin, [kernelEntry], {
  env: { ...process.env, ELECTRON_RUN_AS_NODE: "1", NOIR_DATA_DIR: dataDir },
  detached: true,
  windowsHide: true,
  stdio: ["ignore", logFd, logFd],
}).unref();
```

`detached` and `unref()` are what let the child outlive Electron; `windowsHide` keeps a console from
flashing on Windows. `nodeBin` and `kernelEntry` are the constants main already resolves
(`NOIR_KERNEL_ENTRY` / `NOIR_NODE_BIN`, packaged paths otherwise).

Waiting for readiness is the existing `waitForKernel`: poll the runtime file until it names a live
pid. A spawn that exits before writing it is still a startup failure with the same message it has
today.

If the detached spawn itself throws — no node binary, a missing entry — the host retries once as a
plain child (`detached: false`) and records `daemon: false`. `before-quit` then kills that child, as
the app does today, and the app shell shows a banner: "Kernel is not detached; nothing runs after
quit". A user with a broken install keeps working instead of staring at a dead window.

Attach and spawn both end in the same `KernelInfo` (`port`, `token`, `buildMatches`, `daemon`), so
`kernel:info` and everything downstream keep one shape.

The daemon owns its own lifetime: `before-quit` no longer kills a detached kernel, and
`window-all-closed` hides the window instead of quitting. If the tray cannot be created (some Linux
desktops without a status area), the app falls back to quitting on window close, logs the reason, and
`before-quit` stops the daemon — otherwise closing the window would strand a process with no way
back.

| User action | Window | Tray | Daemon |
|---|---|---|---|
| Close the window | hidden | visible | running |
| Tray → Show window | shown | visible | running |
| Tray → Quit | — | gone | **running** |
| Tray → Quit and stop daemon | — | gone | stopped |
| Tray → Stop daemon | hidden | gone, app stays | stopped |
| App launched while a daemon runs | shown | visible | running, attached |

After `Stop daemon` the app stays alive with no kernel; the next launch spawns one. The pane that
needs a kernel reports the existing "Kernel did not start" failure rather than a new state.

## 4. Health and build identity

`startRpcServer` grows one route on the `http` server it already creates:

```
GET /health -> 200 {"status":"ok","pid":<number>,"buildId":"<hex>" | null}
```

Anything else on that listener is `404`, and `/health` never includes the token or the data
directory. Every JSON-RPC path still requires the token on the WebSocket upgrade.

`buildId` is sha256 of the kernel entry file, computed once at startup from `process.argv[1]` — the
same file the app hashes before spawning. A file that cannot be read yields `buildId: null`, which
never equals the app's, so a broken install replaces rather than attaching to something unknown. The
app compares `buildId` only; no wire version is added, because the RPC shape does not change.

The kernel's own claim inspection stops opening a WebSocket to probe a sibling: it calls
`GET /health` and compares `pid`. That drops its 750 ms handshake to one request. Dropping the token
from the probe loses nothing: the probe only runs while the recorded pid is alive, and a process on
this machine that can bind the recorded port and impersonate that pid can already read the runtime
file.

## 5. Replacing a different build

`POST /shutdown` (see §6) with `{"force": false}`:

- `200` — the daemon closed cleanly and exited. Wait for the pid to disappear (deadline 5 s), then
  spawn the new build and attach.
- `409` with `{"live": <n>}` — sessions are live. Show a modal:
  - *Stop and restart* → `{"force": true}`, then spawn;
  - *Keep the old build* → attach anyway; `kernel:info` reports `buildMatches: false` and the app
    shell shows a dismissible banner above the main pane: "Running an older kernel — restart to
    update". Nothing else changes; the daemon serves the RPCs it already has.

"Live" means any session in `starting`, `running`, or `waiting` — the states in which killing the
daemon discards work. `idle`, `error`, and `closed` never block a replacement.

A 404 or a connection failure means the daemon predates this change: send `SIGTERM` to the pid from
the runtime file, wait for exit, spawn. `SIGTERM` is already handled by `apps/kernel/src/index.ts`
and closes the kernel before exiting.

Dev loop: `NOIR_KERNEL_ATTACH=1` skips the build comparison and attaches to whatever answers, so
rebuilding the kernel mid-session does not raise the dialog on every launch.

## 6. Shutdown

```
POST /shutdown            Authorization: Bearer <runtime token>
body {"force": false}     200 {"stopped": true}
                          409 {"stopped": false, "live": <n>}   when force is false and sessions are live
                          401 {}                                when the token is missing or wrong
```

Comparing the token with `timingSafeEqual`, as the WebSocket upgrade already does.

With `force: true` the handler interrupts live sessions through the existing cancel path, records
them `interrupted`, closes the engines, and exits `0`. The runtime file is removed only when it still
names this pid and token (`removeRuntimeFileIfOwned`), the lock likewise, so a shutdown racing a
replacement cannot delete a newer daemon's claim.

`system.shutdown` is deliberately **not** a JSON-RPC method: no client of the data plane needs it,
and adding it would put a process-lifetime verb inside the vocabulary the renderer can call.

## 7. Tray and single instance

One tray icon, created with the window, removed on quit. Menu:

- *Show NoirHarness* — `show()` + `focus()`.
- `<n> automation(s) armed` — disabled line, `No automations` when zero.
- *Stop daemon* — `POST /shutdown {"force": true}`, then remove the tray.
- *Quit* — `app.quit()`. The daemon keeps running.
- *Quit and stop daemon* — shutdown, then `app.quit()`.

The armed count comes from the renderer: the Automations pane already polls `schedule.list` every
15 s, and the same read reports the enabled count to main. The renderer still never touches Electron
directly — `preload.ts` adds `automationsArmed(n)`, a one-way IPC send, next to the existing
`kernelInfo`/`openExternal` bridges. A hidden window is not a destroyed one, so the renderer keeps
polling and the tray stays accurate; with no window yet, the line reads `No automations`.

`app.requestSingleInstanceLock()` guards the tray and the spawn: a second launch focuses the existing
window (`second-instance`) and exits.

## 8. Logging

The detached child's stdout and stderr both point at one append-mode descriptor for
`<dataDir>/logs/kernel.log`. At spawn, if the file exceeds 2 MB it is renamed to `kernel.1.log`
(replacing any previous rotation) and a fresh file is opened. Rotation at spawn keeps it out of the
running process, which cannot rename its own open descriptor on Windows.

The log carries what the kernel already prints — startup line, `kernel.failed` reason, shutdown
reason — and nothing new. Prompts, keys, and file contents are not logged today and this does not
change that; the redaction rules of M1.5 apply to the log like any other sink.

## 9. Failure modes and how each reads

| Situation | Behaviour | User sees |
|---|---|---|
| Runtime file present, pid dead | Spawn, overwrite the file | Nothing; launch is normal |
| Runtime file names a live pid that fails `/health` | Spawn; the existing lock claim decides which instance lives | Nothing, unless both start at once: one exits cleanly |
| Detached spawn fails (missing node, bad entry) | One retry as a child of the app | Banner: the app works, nothing fires after quit |
| Daemon dies while the app is closed | Nothing fires until the next launch | Each schedule's `missed` rows are the record; no separate banner |
| App update with a live turn | Modal | *Stop and restart* / *Keep the old build* |
| App update while idle | Silent replacement | Nothing |
| Two app launches | Second focuses the first and exits | One window, one tray |
| Two daemons over one data dir (race) | Existing claim: one wins, the loser exits non-zero | The app attaches to the winner |
| `Stop daemon` while a turn runs | Force shutdown interrupts it | The session reopens as `interrupted` at the next launch |
| Uninstall with the daemon running | Out of scope; the daemon keeps running | Documented: tray → Quit and stop daemon first |

## 10. Testing

- **Kernel, `/health`:** returns `status`, `pid`, and the entry's `buildId`; any other path is 404;
  the response never contains the token. An unreadable entry yields `buildId: null`.
- **Kernel, `/shutdown`:** 401 without a token and with a wrong one; 409 with `live` when a session is
  `running` and `force` is false; 200 when idle; after 200 the runtime file and lock are gone and the
  process has exited; a second `/shutdown` after the first is a connection failure, not a crash.
- **Kernel, claim inspection:** a sibling that answers `/health` with a matching pid is `running`; one
  that answers with a different pid is `stale`; one that does not answer at all falls back to the
  existing pid+grace rules.
- **Host unit** (`apps/desktop/test/kernelHost.test.ts`, injected spawn/probe/fs): no runtime file
  spawns; matching build attaches without spawning; different build and idle replaces; different
  build and `409` reports "busy" without spawning; 404 falls back to `SIGTERM`; spawn passes
  `detached` and `windowsHide`; a log over 2 MB rotates before the descriptor opens.
- **Tray unit:** labels for zero, one, and several armed schedules; menu action wiring via injected
  callbacks.
- **End to end**, all in `apps/desktop/test/` beside the existing specs:
  1. launch → quit → the recorded pid is still alive and `/health` answers; relaunch → the same pid,
     no second spawn;
  2. create a 1-minute schedule, quit the app, wait for the occurrence, relaunch → the run is in the
     history and its session is in Chats. This is the only test that proves a fire with no window;
  3. tray *Quit and stop daemon*, then relaunch → a new pid.

Every spec now leaves a process behind that the app no longer kills. The shared harness grows a
teardown that reads the spec's own `<dataDir>/runtime/kernel.json` and shuts that pid down, so a run
leaves no daemons and no port holders regardless of how the app exited. E2E (2) depends on this:
the daemon must outlive the closed app, then die with the test.


## 11. Compatibility and rollout

- **Existing installs.** A kernel started by the previous release has no `/health`; the host's 404
  path sends `SIGTERM`, so the first launch after the update replaces it without a dialog.
- **Old app, new daemon.** The old app kills its own child on quit and ignores `/health`; it attaches
  to nothing. Harmless, and it is not a state anyone can stay in: installing the new app replaces the
  binary.
- **No data migration.** No table, column, or protocol shape changes.
- **Rollback.** Rolling back the app leaves a daemon the old build cannot see; stop it from the tray
  first, or send `SIGTERM` to the recorded pid.
