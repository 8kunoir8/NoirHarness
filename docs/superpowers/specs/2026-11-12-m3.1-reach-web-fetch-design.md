# M3.1 Reach Layer (`web.fetch`) Design Specification

- Date: 2026-11-12
- Status: approved in conversation; awaiting review of this file
- Scope: the first half of M3's "reach layer" — one outbound-read tool for the native engine

## 1. Intent

The agent can read the workspace and run commands, but it cannot read the web. The `network`
permission category has existed since M1 with nothing behind it: `permissionCategory` maps
`kind: "fetch"` to `"network"`, and no tool emits `fetch`. This milestone puts the first tool behind
that gate.

Success: a native-engine session can call `web.fetch` with a URL, the user sees one approval card
titled with that URL, and the model receives readable text from the page — not a binary blob, not the
site's navigation repeated three times, and never a request to an address it should not reach.

Non-goals:

- Search, crawling, POST, custom headers, cookies, authentication, or browser rendering. One GET.
- ACP. The ACP agent brings its own tools, exactly as it does for MCP.
- Boilerplate removal beyond semantic landmarks. Extraction is faithful to the DOM; it is not a
  readability scorer.
- Image, PDF, or media download. A non-text content type is refused with its type, not returned.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Engines | Native only | The ACP payload is the agent's own tool surface; M3.0 established the same split for MCP servers |
| Approval | One card per call, `network` policy applies | `allow` in the agent policy skips the card exactly like `shell`; no new consent surface |
| Where it runs | In the engine, in the kernel process | The native engine is already the workspace authority in-process; no RPC hop, no new service |
| HTTP | `node:http`/`node:https` with a validating `lookup` | The address that is validated is the address connected — see §3 |
| Extraction | In-tree tokenizer, no dependency | Zero-runtime-dependency constraint; regex stripping is provably lossy (§5) |

## 3. Transport and the SSRF guard

`http.request`/`https.request`, `redirect` followed by hand, at most 5 hops, every hop re-validated
from scratch.

- Scheme must be `http:` or `https:`. Anything else is refused before a socket is opened.
- Hostnames are resolved inside the `lookup` callback of the request. `net.connect` uses that
  result directly, so validation and connection are the same event — a second resolution cannot
  return a different address (DNS rebinding).
- Refused: loopback (`127.0.0.0/8`, `::1`), RFC1918 (`10/8`, `172.16/12`, `192.168/16`), CGNAT
  (`100.64/10`), link-local (`169.254/16`, `fe80::/10`), unique-local (`fc00::/7`), `0.0.0.0/8`,
  multicast, broadcast, and the `::ffff:` mapping of each.
- Refused by name: `.local`, `.localhost`, `.internal`, `.home.arpa`.
- One private answer fails the whole request; the request does not fall back to a public address.
- The refusal names the host, not the resolved address.
- Sent headers: `User-Agent: NoirHarness/0.1`, `Accept: text/html,application/xhtml+xml,text/plain,application/json;q=0.9,*/*;q=0.8`,
  `Accept-Encoding: identity`. No cookies, no authorization, no caller-provided headers.

## 4. Result shaping

| Content type | Output |
|---|---|
| `text/html`, `application/xhtml+xml` | Extracted text (§5), with relative links resolved against the final URL |
| `application/json`, `+json` | Pretty-printed JSON, capped |
| `text/*`, `application/xml`, `+xml` | Body as-is, capped |
| Anything else | One line: content type, byte length, and that binary content is not returned |

A non-2xx response is reported as `HTTP <status> <reason>` plus the shaped body of the error page —
the model can react; the tool does not throw.

## 5. Extraction

A tokenizer with an element stack, not a chain of regexes, because the three things that make regex
stripping lossy are exactly what a regex cannot see:

1. **Nesting.** `</table>` must close the table opened three levels up, not the nearest tag that
   happened to match.
2. **Element identity.** Only `<code>` is code. `<kbd>`, `<samp>`, `<var>` are text.
3. **Hidden duplicates.** `aria-hidden="true"`, `hidden`, and `display:none` subtrees are dropped
   wholesale — that is what stops a mobile menu from repeating the navigation inside the article.

Output is Markdown-ish: `#` headings, `-`/`1.` lists with depth indentation, `a | b` table rows,
fenced code blocks, inline code. Code content is stashed behind a placeholder before the final
whitespace pass, so indentation and blank lines inside it survive.

**Content landmark.** When the document marks `<main>` or `role="main"`, only that subtree is read.
The landmark is found by the same tokenizer, so `<main>` inside a `<script>` string is not mistaken
for the page's. Measured cost of not doing this: MDN's GET page is 58 KB of sidebar around a 4 KB
article, and the tool's cap would have returned the sidebar.

The `<title>` is read from the whole document (it lives in the head) and emitted as the first
heading unless the body already starts with it.

Extraction is lossy by design and the tool description says so: it returns readable text, not the
document.

## 6. Limits

| Limit | Value |
|---|---|
| Total request time | 20 s, aborted by the turn's `AbortSignal` |
| Idle between chunks | 10 s |
| Downloaded body | 2 MiB (the stream is destroyed past it) |
| Returned text | 64 KiB via the engine's existing `truncate()` |
| Redirects | 5 |

## 7. Permissions

`web.fetch` reports `kind: "fetch"`; `EngineManager.permissionCategory` already maps that to
`"network"`, so the kernel needs no change. `ApprovalKind` in the engine gains `"fetch"`. The
approval title is `Fetch <url>`.

The policy decision is the gate, not the SSRF guard: with `network: allow` the tool runs without a
card, exactly as `shell: allow` does for `shell.exec`. With `network: reject` it returns
`PERMISSION_DENIED` without a socket.

## 8. Testing

- `packages/engines/native/test/htmlText.test.ts` — structure, hidden subtrees, landmark scoping,
  malformed input. (Implemented; 24 tests.)
- `packages/engines/native/test/web.test.ts` — against a loopback `node:http` server: HTML
  extraction end to end, JSON pretty-print, unknown content type refusal, non-2xx, redirect chain,
  redirect to a private address refused, 2 MiB cap, abort mid-stream, and every refused host
  (`127.0.0.1`, `localhost`, `10.0.0.1`, `[::1]`, `169.254.169.254`, `file:///etc/passwd`,
  `http://foo.local`).
- The loopback tests need a private address, so `fetchPage(url, signal, options)` is exported with an
  explicit `allowPrivate` option. `runTool("web.fetch", …)` never passes it; the security tests call
  the tool, not the seam.

## 9. Risks

1. **Extraction fidelity.** No layout, no CSS visibility beyond inline `style`, no table spanning.
   Accepted: the tool promises readable text. The tokenizer covers the structures that change meaning
   (headings, lists, tables, code, links).
2. **Landmark absence.** A page without `<main>` returns its chrome too. Accepted: without a
   per-page heuristic there is no better signal, and the cap plus the model's own judgement handle it.
3. **Charset.** Bodies are decoded as UTF-8 regardless of `charset=`. Non-UTF-8 pages produce
   replacement characters. Accepted for now; the header is inspected but not acted on.
4. **Redirects across origins** are followed after re-validation. There is no credential to leak
   (the tool sends none), so this is allowed.
