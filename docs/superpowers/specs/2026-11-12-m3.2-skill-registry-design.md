# M3.2 Skill Registry Design Specification

- Date: 2026-11-12
- Status: implemented — installing, pinning, updating, and removing skills from a git URL or a local directory.
- Scope: the last M3 item — installing, versioning, and removing skills from a source

## 1. Intent

M1.4 made skills discoverable: two roots on disk, hashed, enable/disable, a viewer, and a
materialized engine set. What it did not do is answer *where a skill came from*. Every skill today is
either hand-placed or already present; there is no install, no version, and no way to update one
without editing files by hand. The base design defers exactly this: "Registry, versioning, and
distribution are M3."

Success: a user pastes a public git URL (or picks a local directory) in the Skills panel, sees the
skill appear with its commit and content hash, and later updates it — seeing that the hash changed
before anything is replaced. Removing it leaves no trace in either the disk root or the engine set.

Non-goals:

- No hosted catalog, no search, no publishing, no accounts. There is nothing to browse.
- No ACP involvement. Skills reach the engine through the materialized directory, as in M1.4.
- No dependency installation, no script execution from a skill, no `postinstall`. A skill is files.
- No automatic update. Only a user can move a pin.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Storage of provenance | One `skill_sources` table | The `skills` table is rewritten on every scan; provenance must outlive a rescan and is not derivable from disk |
| Version pin | Commit SHA **and** SHA-256 of the content | A SHA identifies a revision of a repository; the hash identifies the bytes on disk, which is what the engine reads |
| Update gate | Caller passes `expectHash`; mismatch refuses | Checking then updating is two round trips, and the remote can move between them. The value shown to the user is the value enforced |
| Source kinds | `git` and `local` | A shared directory is the common case for a team without a registry service |
| Transports | `https://` and a local directory path | No credentials, no ssh-agent, no prompt. Anything else is refused before git runs |
| Where code lives | `packages/kernel/src/skillSources.ts` | `skills.ts` owns discovery and materialization; install is a different concern with its own failure modes |
| Git invocation | `execFile`, argv array, `--`, allowlist + `protocol.ext.allow=never` | Two independent refusals, because one regex is how M3.1's `ext::` class of bug gets through |

## 3. Source records

Migration `8` in `migrations.ts`.

```sql
CREATE TABLE skill_sources (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL DEFAULT '',
  scope TEXT NOT NULL,
  name TEXT NOT NULL,
  kind TEXT NOT NULL,            -- 'git' | 'local'
  url TEXT,                      -- git URL, or absolute path for 'local'
  ref TEXT,                      -- branch/tag as given; NULL when the remote HEAD was used
  commit_sha TEXT,               -- resolved commit for 'git'; NULL for 'local'
  hash TEXT NOT NULL,            -- SHA-256 as `hashSkillDir` computes it
  installed_at INTEGER NOT NULL,
  UNIQUE (workspace_id, scope, name)
);
```

`workspace_id` is `""` for global rows, matching `skills`. A row is created only by a successful
install or update; a skill placed on disk by hand simply has no row and is reported as
`source: null`. Losing the table loses provenance, not skills.

`SkillView` gains this field, `null` for a hand-placed skill:

```ts
source: z.object({
  kind: z.enum(["git", "local"]),
  url: z.string(),
  ref: z.string().nullable(),
  commit: z.string().nullable(),
  hash: z.string(),
  updateAvailable: z.boolean(),
}).nullable()
```

`updateAvailable` is only true when a `checkUpdate` has been run and returned a different commit or
hash; it is not computed during `list`, because `list` must not touch the network.

## 4. Operations

All four take `workspaceId?` and are scoped exactly like `skill.setEnabled`.

| Method | Params | Behaviour |
|---|---|---|
| `skill.install` | `source` (`kind`, `url`/`path`), `ref?`, `scope` | Fetch, validate, hash, copy into the scope root, insert the source row, materialize |
| `skill.checkUpdate` | `scope`, `name` | Fetch again **without writing**, return `{ commit, hash, changed }`. Network only |
| `skill.update` | `scope`, `name`, `expectHash` | Fetch, refuse if the fetched hash !== `expectHash`, else replace in place and re-record |
| `skill.remove` | `scope`, `name` | Delete the directory, the source row, the enabled flag, materialize |

**Install refuses an existing name** in the same scope with `conflict`. Overwriting is `update`,
which is a different decision and a different confirmation.

**Install into the other scope than an existing name** is allowed: a project skill shadowing a
global one is exactly the precedence M1.4 defined, and it is reported as `shadowed`, not merged.

**Update replaces the directory atomically**, using the same `rename`-aside sequence `materialize`
already uses, so a failed update leaves the previous copy in place.

`remove` on a skill with no source row is allowed — it deletes the directory and reports
`source: null`. It refuses any path that is not inside a scanned root.

## 5. Fetching

### 5.1 Source validation

Before any process starts:

- A `git` source MUST parse as a `URL`. `https:` is accepted anywhere; `http:` is accepted only when
  the host is `127.0.0.1`, `localhost`, or `[::1]`, so no credential-free fetch crosses a network in
  the clear. `ssh:`, `git:`, `file:`, and a bare `host:path` are refused with `invalidParams`.
- A `local` source MUST be an absolute path to an existing directory, and MUST NOT be a symlink. The
  path is copied, never linked.
- The URL MUST NOT contain userinfo (`https://user:token@host/...` is refused), consistent with
  `web.fetch`.
- `ref`, when given, MUST match `^[A-Za-z0-9][A-Za-z0-9._/-]{0,127}$`. It is passed as its own argv
  element, never interpolated into a shell string.

### 5.2 Git

```
git -c protocol.ext.allow=never -c core.symlinks=false -c credential.helper= \
    clone --depth 1 --no-recurse-submodules --single-branch [--branch <ref>] -- <url> <tempdir>
```

- `ext::` is a remote command execution transport. It is refused twice: the scheme allowlist rejects
  it, and `protocol.ext.allow=never` covers a config or redirect that produced one anyway.
- `--` terminates options, so a URL beginning with `-` is not an option.
- `GIT_TERMINAL_PROMPT=0` and `GIT_ASKPASS=` are set, so a private URL fails in milliseconds instead
  of waiting on a prompt that no one can answer.
- Timeout 30 s, `maxBuffer` 4 MiB, `windowsHide: true`.
- After the clone, `git rev-parse HEAD` yields the pinned commit.

### 5.3 Caps

The clone is measured before anything is copied into a root:

| Limit | Value | On exceed |
|---|---|---|
| Files per skill | 200 (`MAX_SKILL_FILES`) | refuse, delete temp |
| Total bytes | 8 MiB (`MAX_SKILL_BYTES`) | refuse, delete temp |
| `SKILL.md` | 1 MiB (`MAX_SKILL_FILE_BYTES`) | refuse, delete temp |
| Clone working tree | 32 MiB | refuse, delete temp |

The first three constants are private to `skills.ts` today; they are exported so the staging check
uses the same numbers rather than a second copy. A symlink inside the source is skipped by
`copySkill`, which already does that for the materialized set.

The temp directory is under the data dir (`<dataDir>/skill-staging/<uuid>`) and is removed in a
`finally`, including on refusal.

### 5.4 `SKILL.md` is untrusted

The name comes from the fetched file and becomes a directory name. `SKILL_NAME` validation happens
before any path is joined; a name that does not match is refused with the reason, matching the
warning format `discoverSkills` already produces.

## 6. Error handling

- Network failure, timeout, non-zero git exit: `internal` with git's stderr, first 2 KiB.
- Refused transport, bad `ref`, missing local path: `invalidParams`.
- Name already present: `conflict`.
- Update with a mismatched `expectHash`: `conflict`, message carrying both hashes.
- A failed update leaves the old directory, the old source row, and the old hash untouched.

## 7. Permissions

Install and update perform network I/O, but they are **user-initiated from the UI**, not triggered
by an agent; no approval card is raised and the `network` policy category does not apply. This is the
same distinction M3.0 drew for MCP server configuration. If a tool ever triggers an install, it goes
through the `network` category like `web.fetch`.

## 8. Surfaces

- Protocol: the four methods, `SkillSourceView`, and `source` on `SkillView`.
- Kernel: `skillSources.ts`, driven from `index.ts` beside the existing handlers.
- Desktop: an install control (URL or path, scope selector) and, per row, the source with its short
  commit, with an update action present only when `checkUpdate` reports a change. The update
  confirmation shows old → new hash.

## 9. Testing

Kernel tests use **real git repositories** created per test in a temp dir. The `local` kind needs no
git at all. For the `git` kind, the test creates a repo, commits a skill, clones it `--bare`, and
serves it with `git http-backend` behind a `node:http` server on `127.0.0.1` — the smart protocol,
because the measured dumb protocol rejects `--depth 1` outright ("dumb http transport does not
support shallow capabilities"). That exercises the real clone path with no external network and no
certificate, and it is why §5.1 allows `http:` on loopback.

Tests that must fail without the change:

- `ext::`, `ssh://`, `http://<non-loopback>`, and `file://` refused before any process spawns (the
  spawn is stubbed and asserts it was never called).
- A URL with userinfo refused.
- Install refuses an existing name; installing the same name into the other scope succeeds and
  shadows.
- Update with a stale `expectHash` refuses and leaves the directory byte-identical.
- Update with the current `expectHash` replaces the content and records the new commit and hash.
- `checkUpdate` writes nothing (directory and DB unchanged).
- Remove deletes the directory, the row, and the engine copy, and returns the remaining list.
- A `SKILL.md` whose name contains `..` or a separator is refused before any path is joined.
- A source containing a symlink, or over the file cap, is refused and its temp dir is gone.

Desktop: the install action round-trips in `skills.test.tsx`; an update badge appears only after
`checkUpdate` reports `changed`.

## 10. Risks

1. **The git fixture on Windows.** Measured: a smart-HTTP clone through `git http-backend` over a
   loopback `node:http` server succeeds in about a second, including `--depth 1` and `rev-parse`.
   If `http-backend` is absent from a machine's git, the git-kind tests skip with an explicit
   message rather than pass silently.
2. **Credential prompts.** `GIT_TERMINAL_PROMPT=0` covers the CLI; a configured credential helper
   could still surface a GUI prompt. `credential.helper=` is cleared on the command line to remove
   the remaining path.
3. **Repository size.** `--depth 1` still transfers one full tree. The 32 MiB cap bounds the result
   after transfer, not the transfer. Accepted for a URL the user pasted.
4. **A skill is instructions.** Installing one changes what an agent does. The hash pin makes an
   update visible; it does not make the content safe. Same boundary as M1.4: the user chooses
   skills, the harness does not curate them.
