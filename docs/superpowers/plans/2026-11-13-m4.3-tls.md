# M4.3 TLS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The LAN listener serves only over TLS with a self-signed certificate generated in-process, so the device cookie is never sent in cleartext.

**Architecture:** `tls.ts` encodes the smallest valid X.509 v3 certificate by hand (DER + ECDSA P-256), stores it under `<dataDir>/tls`, and reissues when the machine's addresses change. `remoteAccess.ts` swaps `createRpcListener`'s plain `http.Server` for an `https.Server` and threads the scheme through the guard, the cookie, and the URL it advertises.

**Tech Stack:** Node 24, `node:crypto` (`generateKeyPairSync`, `sign`, `X509Certificate`), `node:https`, `ws`, vitest, Playwright Chromium.

**Spec:** `docs/superpowers/specs/2026-11-13-m4.3-tls-design.md`

## Global Constraints

- Node >= 24, TypeScript strict (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`), ESM with `.js` extensions, **zero new runtime dependencies**.
- One commit per task on `main`; never branch, never push, never amend.
- Never log the private key, the cookie, or the pairing code. The fingerprint is public and is logged only where the pane shows it.
- Targeted suites per task; one full gate at the end against the 934 unit / 17 e2e baseline.
- `exactOptionalPropertyTypes`: optional fields are spread in, never assigned `undefined`.

## Review Focus

- **DER correctness.** A certificate that parses but does not verify is worse than a warning; the test signs and verifies, and `X509Certificate` parses the same bytes. Task 1.
- **SAN completeness.** Every address the pane might advertise must be in the cert, or the browser warns for the wrong reason. Task 1.
- **No plaintext path.** The LAN listener must not answer `http` at all — not with 400, not with a redirect. Task 2.
- **`Secure` cookie.** Set over TLS only; the loopback path is unchanged. Task 2.
- **Loopback untouched.** `startRpcServer`, its token auth, and its `http://` URL do not change. Task 3.

### Task 1: The certificate

**Files:**
- Create: `packages/kernel/src/tls.ts`
- Test: `packages/kernel/test/tls.test.ts`

**Change:** `ensureCertificate({ dir, hosts })` → `{ certPath, keyPath, fingerprint, issued: boolean }`.
DER helpers (`seq`, `set`, `int`, `oid`, `utc`, `bitString`, `explicit`, `octet`) stay private.
`tls.ts` exports `certificateFingerprint(pem)`, `certificateCovers(cert, hosts)`, and
`generateCertificate({ commonName, hosts })` for the tests.

**Verification:** `pnpm exec vitest run test/tls.test.ts` — parses with `crypto.X509Certificate`;
`subjectAltName` lists every IPv4 the machine has; `verify(publicKey, tbs, signature)` holds;
`checkIP("127.0.0.1")` passes; second call reuses (`issued: false`); changing `hosts` reissues
(`issued: true`) with a different fingerprint; key file mode is `0600` on POSIX.

### Task 2: The listener

**Files:**
- Modify: `packages/kernel/src/rpcServer.ts` (`createRpcListener` takes TLS material)
- Modify: `packages/kernel/src/remoteAccess.ts`
- Modify: `packages/kernel/src/devices.ts` (`deviceCookieHeader(value, { secure })`)
- Modify: `packages/protocol/src/rpc.ts` (`RemoteStatusResult.fingerprint`)
- Test: `packages/kernel/test/remoteAccess.test.ts`

**Change:** `createRpcListener` accepts `tls?: { key: string; cert: string }` and builds an
`https.Server` when present. `RemoteAccess.enable()` ensures the certificate first, passes it, and
advertises `https://…`; `guard` compares `Origin` against the listener's own scheme; the redeem route
sets `Secure`.

**Verification:** `pnpm exec vitest run test/remoteAccess.test.ts` — the suite's `send` helper grows a
`secure` flag so existing cases keep exercising the same code over TLS; a plain `http` request to the
TLS port fails; the cookie carries `Secure`; `status().url` starts with `https://`.
