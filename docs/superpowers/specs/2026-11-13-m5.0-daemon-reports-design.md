# M5.0 — The daemon reports in

Status: design.

## 1. Intent

M4.1 made runs fire with no window; M4.2 made them reachable from a phone. What none of it does is
tell the person. Today a scheduled run that starts at 06:00 and fails at 06:03 is discovered whenever
the app is next opened, and a kernel that dies between launches is not noticed at all.

Three gaps, one milestone:

1. **Outcomes.** A scheduled run finishing or failing raises an OS notification.
2. **Survival.** The app notices a kernel that stopped answering and restarts it.
3. **Presence.** The kernel can start when the machine does, so a 06:00 schedule has something to
   fire on.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Who notices | Electron main, over its own socket to the kernel | The window may not exist; the renderer cannot be the witness |
| Socket client | the global `WebSocket` in Electron's Node | No dependency; the same frame shape the renderer already speaks |
| What counts as "scheduled" | `session.created` carries the `scheduleId` | The session row already has it; the payload just did not say so |
| When to notify | `turn.completed` / `turn.failed` on a session that was created with a `scheduleId` | Start and finish are the two things a person cares about; deltas are noise |
| Duplicate runs | one notification per run, keyed by session | The kernel can replay on reconnect; the app remembers what it said |
| Notification failures | swallowed | A desktop that cannot show a notification must not take the turn with it |
| Supervision | poll `/health` every 15 s, respawn after 2 consecutive failures, at most once a minute | A busy machine must not be read as a dead one; a crash loop must not become a spawn loop |
| start-at-login | `app.setLoginItemSettings`, persisted in `<dataDir>/desktop.json` | Electron owns the platform call; the preference is the app's, not the kernel's |
| Observability in tests | `NOIR_NOTIFY_LOG` writes one line per notification | E2E can prove the notification happened without a notification daemon |

## 3. The event

`session.created` payload gains an optional `scheduleId: string`. Additive: every existing reader
ignores it, and the field is absent for a session a person started.

Main keeps a `Set<string>` of scheduled session ids and a `Set<string>` of sessions it has already
notified about, both bounded by the sessions it has seen since launch.

Notification text:

- finished — `Scheduled run finished`, body `<schedule title or session title>`
- failed — `Scheduled run failed`, body `<message>` truncated to 140 characters

## 4. Supervision

`main.ts` polls `http://127.0.0.1:<port>/health` on a 15 s timer using the pid and token it already
holds. Two consecutive failures → `hostKernel` runs its existing attach-or-spawn path. A respawn is
attempted at most once a minute; a second failure inside the window leaves the app showing *kernel
stopped* in the status line and the tray, and it does not keep trying silently.

A kernel that answers with a different pid is adopted: that is a kernel someone restarted by hand,
and fighting it would be worse than following it.

## 5. Start at login

Tray menu gains a checkbox item. The choice lives in `<dataDir>/desktop.json`
(`{ "openAtLogin": true }`), applied on launch via `app.setLoginItemSettings({ openAtLogin, args: [] })`
so the stored value and the OS state agree even after an OS reset.

## 6. Non-goals

Notifications for interactive turns; a notification when a *pairing code* is used; waking the machine;
a scheduler in the app; restarting the kernel when the *data directory* is broken (that is a startup
failure, shown as one).

## 7. Failure modes

| Situation | Behaviour |
|---|---|
| OS notifications unavailable (headless, no daemon) | `Notification.isSupported()` false → nothing is shown, nothing throws |
| Kernel socket refuses (wrong build) | Main retries with backoff; the tray already reports the build mismatch |
| Kernel exits while a notification is pending | The notification has already been sent or not; no queue |
| Two app instances | The single-instance lock means one main process, so one witness |

## 8. Testing

- `notifications.test.ts` (node env): a scheduled `session.created` then `turn.completed` notifies
  once; a second `turn.completed` does not; an interactive session never notifies; a failed turn
  names the failure.
- `supervision.test.ts`: two failures respawn, one does not; the rate limit holds; a changed pid is
  adopted, not replaced.
- `settings.test.ts`: default is off; write and read round-trip; a corrupt file reads as defaults.
- E2E (`daemon-fire.spec.ts`): with `NOIR_NOTIFY_LOG` set, a fire with no window writes a line.
