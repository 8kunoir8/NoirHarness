# M6.0 — Rewind

Status: design. Approved in conversation 2026-11-14; rewritten here for review.

## 1. Intent

A turn that ruins the work is discovered after it ends. Today the only remedies are `session.fork`
(a copy of the transcript under a new id, files untouched) and git by hand. Rewind makes the
transcript's own history the control: **stand at a user prompt, restore the workspace and the
conversation to the moment before it, retry.**

What a user does:

1. Hovers their own prompt in the transcript, picks **Rewind to before this prompt**.
2. Reads a confirm dialog: how many files come back, how many are deleted, how many were created
   after and are removed, and how many files the snapshot could not capture.
3. Confirms. The files are back, the turns from that point forward leave the transcript behind one
   marker line (**Rewound to before this prompt**), and the composer is empty and ready for the
   retry — or one click on the marker's **Load the prompt again** away from it.

Success is: the retried turn sees the files and the conversation as they were, and no earlier turn
was lost from the log.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| What a rewind undoes | Files **and** conversation, as one action | Two buttons for one mistake is a worse tool; git is already there for files-only |
| Where it lands | In place — the same session continues from the cut | A fork exists already; rewind is the other verb |
| Snapshot mechanism | Git plumbing in a hidden git dir per workspace | Correct for every engine, byte-exact, deduped, no new dependency; the workspace need not be a git repo |
| The user's repo | Never used: the store is its own `GIT_DIR`, and the workspace's `.git` is never opened | A harness that mutates someone's index or refs is a bug report |
| Heavy directories | Always excluded, independent of `.gitignore` | A 300 MB `node_modules` copy is never what was meant |
| When | At **turn start**, synchronously, before the engine spawn | The boundary is exact, and turn start already pays for profile materialization |
| Snapshot failure | Never fails the turn; the row records why and that turn has no rewind | A checkpoint is a convenience; the turn is the product |
| Transcript history | Append-only; `session.rewound` names the cut, projections filter | ADR-0002: the log is the transcript of record |
| Discarded range | `[cutSeq, rewindEventSeq)` — computed from seq, so rewinds stack | Works for a rewind of a rewind without a second watermark |
| Restore conflicts | Show counts, restore on confirm | One meaning, no hidden guard rails; the count is the guard |
| A running turn | Refused, anywhere in that workspace | A restore under a streaming turn would fight it for the same files |
| Engine memory (OMP/ACP) | Not truncated; the marker says so | The kernel has never replayed history into those engines (`notes/2026-11-13-omp-rpc-mode.md:134`); rewriting another tool's session file is not ours to do |
| Engine memory (native) | Engine disposed, next prompt respawns from filtered events | `reconstructHistory` then rebuilds exactly the visible turns |

## 3. The snapshot store

One repository per workspace, under the data directory, never inside the workspace:

```
<dataDir>/checkpoints/<workspaceId>/            # the store: a repository of its own, so it is `<store>/.git`
<dataDir>/checkpoints/<workspaceId>/.git/index  # git's own index: the stat cache that makes this cheap
<dataDir>/checkpoints/<workspaceId>/ignore      # the forced excludes, outside the work tree
```

`git init --quiet <store>` makes `<store>` a repository, so the git dir, its index, and its
`index.lock` are all under `<store>/.git/`. The work tree is never `<store>`: `core.worktree` names
the workspace, which is why neither the store, its index, nor its ignore list can be captured.

Config written once at creation:

| Key | Value | Why |
|---|---|---|
| `core.worktree` | the workspace root | lets every command run without a `--work-tree` flag |
| `core.bare` | `false` | it does have a work tree; the *git dir* is just elsewhere |
| `core.autocrlf` | `false` | this machine has `autocrlf=true`; a restore must write the bytes it read |
| `core.safecrlf` | `false` | no "will be replaced by CRLF" refusal on mixed content |
| `core.hooksPath` | an empty directory in the store | a checkpoint never runs user hooks |
| `core.fsmonitor` | `false` | nothing to watch; a stale monitor must not answer for us |
| `core.excludesFile` | `<store>/ignore` | the forced excludes, one list per workspace (the data dir is added when it sits inside the workspace) |
| `gc.auto` | `6700` (git default) | objects are deduped; pruning is git's job, not a second policy |

Forced excludes, on top of the workspace's own `.gitignore` files:

```
.git/  node_modules/  dist/  build/  out/  release/  target/  .next/  .cache/  vendor/  coverage/
```

Paths inside `<dataDir>` are never captured: when it lies under a workspace root, the exclude file
naming it is written work-tree-relative.

One tree per turn start, pinned by a ref so no `gc` can prune it:

```
refs/noir/<sessionId>/<checkpointId>
```

The commit is created with `commit-tree` and fixed identity (`NoirHarness <checkpoints@noir.local>`),
so a machine without `user.name` still snapshots.

### Rows

Migration 11 adds one table; nothing existing changes shape.

```sql
CREATE TABLE checkpoints (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  turn_id TEXT, seq INTEGER NOT NULL, tree_sha TEXT, commit_sha TEXT,
  label TEXT NOT NULL,                -- "turn" | "pre-restore"
  created_at INTEGER NOT NULL,
  not_captured INTEGER NOT NULL DEFAULT 0,
  error TEXT
);
CREATE INDEX idx_checkpoints_session ON checkpoints (session_id, seq);
```

No foreign key to `workspaces` on purpose: a workspace row can be removed while a rewind is still
offered from the transcript, and the store directory is keyed by the same id.

`not_captured` is filled at capture time from
`git status --porcelain -z --ignored=traditional --untracked-files=all`, counted by path and capped at
5 000. It is a disclosure, not an inventory: the list itself is not stored, and a row at the cap says
5 000 whether or not more were hidden.

### Capture

```
git add -A                                         # work tree → index (stat cache: only changed files are read)
git write-tree                                     # tree object
git commit-tree <tree> -m "checkpoint"             # commit object
git update-ref refs/noir/<session>/<checkpoint> <commit>
```

Cost: the first snapshot in a workspace reads every non-excluded file; every later one reads only
files whose `mtime`/`size`/`ino` changed. No hashing pass, no second store, no size accounting of our
own. The index lives with the repository, so the stat cache survives a kernel restart.

### Refused inputs

- **`.gitattributes` with `filter=lfs`** in the workspace root → no snapshots at all for that
  workspace; rows record `LFS worktrees are not supported`. Git would capture the pointer file and a
  restore would write the pointer over the content. Detected once per snapshot from the root file.
- **Free space below 500 MiB** (`fs.statfs` on the data dir) → the snapshot is skipped with that
  reason. Checked before `add -A`.

Every other failure (permissions, a file vanishing mid-walk, `git` returning non-zero) is recorded on
the row and never thrown into the turn.

## 4. When a snapshot is taken

`engineManager.startTurn` calls the checkpoint store synchronously — awaited, before `ensureEngine`
and before `turn.started`, inside the same try that already handles engine-spawn failure:

```ts
const checkpoint = await checkpoints.capture({ sessionId, workspaceId, workspaceRoot, turnId, seq });
```

The cut is `events.nextSeq(sessionId)`, read **before** the prompt's events are emitted, so the
prompt itself is at or after the cut and a rewind hides it along with the turn: everything at or
after `seq` belongs to the turn and is what gets cut.

A queued turn cannot use the seq its prompt took — that prompt was emitted mid-turn, before the
running turn's tail. Its capture therefore takes `events.nextSeq` at the moment the queued turn
starts draining, which is exactly the seq `turn.started` is about to take (the capture runs before
that emit).

`capture` is off the critical path only in the sense that it is a `git add` of the delta; it is
awaited, because a snapshot taken after the engine starts could see the turn's own writes.

## 5. Restore

`checkpoint.restore({ sessionId, checkpointId })`:

1. **Refuse** (`conflict`, `A turn is running in this workspace`) when any session in that workspace
   is mid-turn, (`conflict`, `A rewind is already running in this workspace`) when a rewind is in
   flight there, or (`conflict`, `A checkpoint plan is still running in this workspace`) while
   `checkpoint.plan` is scanning the same workspace — a plan's `add -A` reads the work tree into the
   very store index this restore's `read-tree` replaces, so neither may run inside the other.
   `checkpoint.plan` refuses symmetrically, with `A rewind is already running in this workspace`
   while a restore holds the store and `A checkpoint plan is already running in this workspace`
   while another plan holds it; the renderer disables the action with the same reason. The refuse
   is one synchronous check-and-set with the reservation that follows it, so a turn either started
   before this scan and is seen, or is refused by `prompt` — no turn is mid-flight while the work
   tree is rewritten.
2. **Availability** (the kernel's `availability`, the same one `checkpoint.list` reports as
   `available`): `git` present, the workspace on disk, not an LFS work tree, enough free space, and
   the workspace root not the data dir itself. Any failure refuses with `conflict` and that reason,
   before the queue or the work tree is touched.
3. **Prepare** (`prepareRestore`) — every step that can still refuse runs here, in this order:
   - resolve the row; a checkpoint without a tree is `notFound` with the reason it recorded;
   - capture the current work tree as an implicit checkpoint (`pre-restore`) so a mistaken restore is
     one click on the marker's **Undo this rewind** away. This is the same `add -A` the diff needs,
     and its own failure refuses the whole restore with `The current state could not be captured: …`
     — a rewind whose undo cannot be taken is not a rewind;
   - predict the counts with `git diff-index --name-status --cached <snapshot-tree>`, by git's own
     status class: `M` → `restored`, `D` (in the tree, gone from the work tree) → `deleted`, `A` (in
     the work tree, absent from the tree) → `removed` — and list the changed paths behind them;
   - `git read-tree <snapshot-tree>`: the store's index becomes the snapshot's tree. No work-tree
     byte has moved yet, so a store that cannot be written (a held `index.lock`, a full disk) fails
     here instead of halfway through a restore.
4. **Release the session's turn side**: drop the queued turns, clear `state.usage`, and dispose a
   native engine so its next spawn rebuilds history from the visible events. This happens *before*
   the marker, so a dropped queued turn's `turn.failed` lands inside the range the restore is about
   to abandon; otherwise the retry's replay would show a turn nobody asked for. For ACP/OMP the
   engine is left as it is: it keeps its own memory, which the marker says out loud.
5. **Apply** (`applyRestore`) — nothing here except a per-path failure may refuse, because the queue
   is already gone and the marker must land. Per path: `git checkout-index --force -z --stdin` for
   the modified and the deleted paths (the index was set to the snapshot in step 3, so this writes
   the captured bytes and reads nothing from the live work tree), and `rm` for the created ones. A
   failure is collected into `failed` and the rest still applies: one file locked by an editor is a
   count, not an aborted restore. Ignored files are in neither list and are left alone.
6. Set the `pre-restore` row's `seq` to `events.nextSeq(sessionId)`, then append `session.rewound`:
   one synchronous block, no await between the two, in that order. `append` assigns exactly that
   seq, so the row sits at the range's `to` — listed, and at the address the marker's **Undo this
   rewind** uses (a `pre-restore` row has `turnId: null`, so only its seq can find it). The
   prediction is exact because the rewind reservation holds the workspace: no other turn or restore
   can append to the session between `nextSeq` and the append. Writing the row *after* the marker
   instead would reopen a crash window — a kill between the two writes leaves the undo row inside
   the range its own rewind created, unlisted, with no restart to repair it.
7. The append carries the counts, the failures, `promptSeq`, the engine kind, and whether the
   engine was left un-rewound.

A restore never deletes the abandoned rows. `turns`, `events`, `approvals`, `file_changes` and
`checkpoints` all stay; the log is append-only, and `events.visible` is what hides the range.

## 6. The event and the cut

New event type `session.rewound`, payload:

```ts
z.object({
  cutSeq: z.number().int().nonnegative(),      // events with seq >= cutSeq and before this event are abandoned
  checkpointId: z.string(),
  promptSeq: z.number().int().nullable(),      // the removed prompt's seq; null when the cut has no user message
  restored: z.number().int().nonnegative(),    // M: content the restore rewrote
  deleted: z.number().int().nonnegative(),     // D: gone since the snapshot, put back from the tree
  removed: z.number().int().nonnegative(),     // A: created since the snapshot, deleted by the restore
  failed: z.number().int().nonnegative(),      // paths git refused; 0 in the normal case
  notCaptured: z.number().int().nonnegative(), // ignored/excluded paths, disclosed at confirm time
  engine: EngineKind,                          // "acp" covers both OMP transports
  engineNotRewound: z.boolean(),               // true when the engine keeps its own memory: acp
})
```

`events.visible(sessionId, sinceSeq = 0)` — one kernel read, `events.list(sessionId, sinceSeq)`
filtered so that a `session.rewound` event at seq `r` with `cutSeq c` hides everything in `[c, r)`.
Multiple rewinds produce multiple ranges; a range that a later range contains is redundant and
harmless.

It is **the** seam, used by:

| Consumer | Effect |
|---|---|
| `session.subscribe` replay (`index.ts:568`) | the renderer never receives abandoned events |
| `engineManager.ts:719` history replay | a native respawn does not tell the model about discarded turns |
| `eventStore.copyPrefix` (fork) | a fork of a rewound session copies the visible prefix only |
| session meta (`lastEventSeq`, `lastEventAt`, `pendingApproval`) | computed from the newest visible event, so the list's timestamp and its approval badge follow the marker instead of the abandoned turn. `SessionView` carries no usage or turn count: the header's usage is renderer-side, assembled from the `usage.updated` events the replay still shows |
| `checkpoint.list` | only checkpoints outside an abandoned range are offered |

`session.rewound` itself is always visible, and its `seq` is above the range it closes.

Cursors: `visible(sessionId, sinceSeq)` and any "replay from here" contract assume everything below
`sinceSeq` is settled. Undoing a rewind is a restore of the `pre-restore` checkpoint, whose row sits
at the first marker's own seq; the new marker therefore hides the earlier one and brings its range
back. That range lies above the cut but below any reader's cursor, so an incremental reader never
learns about the turn that came back. Every reader in this repo replays from 0 after a
`session.rewound` (`useSessionEvents` bumps a generation and re-subscribes with `sinceSeq: 0`), and
a client must do the same.

## 7. Protocol

| Method / schema | Shape |
|---|---|
| `CheckpointView` | `{ id, turnId: string \| null, seq, createdAt, notCaptured, label, error: string \| null }` — bookkeeping only; the counts a dialog needs are the *prediction* of a restore, so they are asked for per checkpoint rather than computed for every row |
| `checkpoint.list` | in: `{ sessionId }`; out: `{ checkpoints: CheckpointView[], available: boolean, reason?: string }` — `available` is false when `git` is missing, the workspace is LFS, or the store is unusable, with a one-line reason the renderer shows instead of the action |
| `checkpoint.plan` | in: `{ sessionId, checkpointId }`; out: `{ restored, deleted, removed, failed: string[] }` — refreshes the index (one `add -A`) and diffs it against the snapshot, without touching the work tree beyond what `add` reads. Called when the dialog opens, and readable while a turn runs (it never writes the work tree). `conflict` while a restore holds the workspace — the shared store index — or while another plan does |
| `checkpoint.restore` | in: `{ sessionId, checkpointId }`; out: `{ ok: true, restored, deleted, removed, failed: string[], eventSeq }`; errors: `conflict` (a turn, a rewind, or a plan holds the workspace, or a precondition failed — the returned message is the reason), `notFound`, `internal` |
| `session.event` | in: `{ sessionId, seq }`; out: `{ event: AgentEvent }`; `notFound` when no such seq. Reads the raw log on purpose: it is how the marker re-fills the composer with an abandoned prompt, and the only read that crosses the cut |
| `system.health` | gains `checkpoints: "ok" \| "unavailable"` and `checkpointReason?: string` — from a `git --version` probe that is cached once it succeeds; a failure is retried once immediately and then re-probed no sooner than 30 s later, so one spawn that loses to a loaded machine cannot disable checkpoints for the life of the process |

`checkpoint.*` replaces the reserved name in the design's method list; `subagent.*` stays reserved.

## 8. UI

- **Turn action.** In `Chat.tsx`, inside the user's own message bubble and only there, a link
  labelled **Rewind to before this prompt** (65 % opacity, full on hover or focus). Hidden when the
  turn has no checkpoint in `checkpoint.list`.
- **Confirm dialog.** An overlay following `QuickOpen`'s `role="dialog"` markup, headed
  **Rewind to before this prompt**, with the hint `The files this turn changed go back; the
  conversation after it goes away.` Opening it calls `checkpoint.plan`; while the plan is computed
  it says `Checking what would change…` with `Rewind` disabled, then the counts
  (`3 files restored · 0 deleted files · 1 created file removed`), any paths that could not be
  applied, and `2 items were not captured and will not move.` when non-zero. A plan or restore
  failure shows its reason in a `role="alert"` and leaves `Rewind` disabled. `Cancel` takes focus
  when the dialog opens — not merely the first tab stop — so `Escape` reaches the container and
  closes the dialog in every phase, including while the plan is still being computed. Only a click
  on `Rewind` does work; it reads `Rewinding…` until the marker lands.
- **Marker.** From `session.rewound`, a divider row headed **Rewound to before this prompt**, then
  `3 restored · 0 deleted · 1 removed`, `1 could not be applied.` when a path failed, the
  not-captured count when non-zero, and `This engine keeps its own memory, so it was not rewound.`
  for an ACP session. Its `Load the prompt again` button calls `session.event` with the payload's
  `promptSeq` — the one read that crosses the cut — and fills the composer with that prompt's text
  without sending it. The marker also carries **Undo this rewind**: the `pre-restore` checkpoint the
  restore captured sits at the marker's own seq (`checkpoint.list` reports it with `turnId: null`),
  so the marker is where its undo belongs — `useCheckpoints` keys those rows by seq in
  `preRestore`, and `Chat.tsx` hangs the action on the marker with a matching `seq`. Confirming it
  runs the same dialog, titled `Undo this rewind`, with the hint `The files this rewind took away
  come back, and the conversation returns to what it was.` and a confirm button reading `Undo`
  (`Undo…` while it applies); the undo is itself a rewind, so its own `pre-restore` row makes it
  undoable in turn.
- **Replay rebuild.** `useSessionEvents` re-runs its `session.subscribe` replay when a `session.rewound`
  for its session arrives, replacing state through the existing buffered/ordered path. No
  incremental truncation logic is introduced; there is one way to build a transcript from events.
- **The abandoned prompt.** The composer starts empty after a rewind. Any user prompt whose seq is
  the payload's `promptSeq` is gone from the transcript, so the marker is the only way back to it.

## 9. Failure modes

| Situation | Behaviour |
|---|---|
| `git` binary missing | `system.health.checkpoints = "unavailable"`; no action anywhere; nothing else changes |
| Workspace root deleted | `checkpoint.list` returns `available: false` with `workspace missing`; a restore that races it refuses |
| Snapshot fails mid-turn-start | Turn proceeds; row has `error`; that turn displays no action |
| Snapshot skipped (low disk, LFS) | Same, with the reason on the row; the dialog for other turns mentions `notCaptured` only |
| Restore interrupted by a kill | Files may be partly restored, and no marker was written, so no **Undo this rewind** exists to click; the `pre-restore` checkpoint was captured before any write, so the state is still recoverable with `checkpoint.restore` |
| Restore while a turn runs | `conflict`, `A turn is running in this workspace`; renderer disabled state |
| Two restores at once | `conflict`, `A rewind is already running in this workspace`, via a workspace reservation held for the whole call |
| Rewind, then fork | The fork copies the visible prefix; its `cutSeq` ranges resolve in the copy because `copyPrefix` filters before copying |
| Rewind, then rewind again | Second range sits inside the first or beside it; both are filtered identically |
| Session deleted | `checkpoints` rows cascade; objects stay until `git gc` prunes unreachable ones — no session ever holds a dangling ref |

## 10. Testing

Unit — kernel (`checkpoints.test.ts`, real `git` on a temp dir):

- capture → modify, create, delete → restore: contents equal the captured bytes, the created file is
  removed, the deleted file is back;
- CRLF bytes survive the round trip with `autocrlf=true` in the user's environment;
- a binary file and a 200 KB text file survive;
- `node_modules/secret.js` is not captured and is untouched by a restore that removes everything else;
- `.gitattributes` with `filter=lfs` yields `available: false`;
- capture with a missing workspace root records an error row and throws nothing;
- `checkpoint.plan` predicts the same three counts the following restore reports;
- `restored/deleted/removed` counts match the mutation set.

Unit — protocol/kernel:

- `events.visible` hides `[cutSeq, r)` across one and two rewinds, and brings an abandoned turn back
  when the rewind that hid it is itself rewound;
- `session.fork` of a rewound session copies only visible events and its own replay is unchanged;
- native history replay excludes an abandoned turn (existing `reconstructHistory` test extended);
- the session meta (`lastEventSeq`, `lastEventAt`, `pendingApproval`) is computed from the visible
  log, so a marker above the abandoned range becomes the session's newest event;
- restore refuses with `conflict`, `A turn is running in this workspace`, while another session in
  the same workspace runs a turn, with `conflict` again while a rewind is in flight there, and with
  `conflict` while a plan holds the store — and the listed checkpoint restores once the plan is
  released; `checkpoint.plan` refuses symmetrically while a rewind holds the store, and plans once
  it is released;
- append-only: no row is deleted by a restore (`turns`/`events` counts unchanged, marker present).

E2E (`rewind.spec.ts`), two tests against the shipped UI and a native engine:

1. A `stream` prompt runs to its reply. The spec then edits the files itself — `seed.txt`
   overwritten, `created.txt` added — to stand in for what the turn wrote, since the mock provider
   writes nothing. **Rewind to before this prompt** opens the dialog, which shows
   `1 file restored · 0 deleted files · N created files removed` (the created count is a floor: the
   engine spawn writes `.noir/skills-engine.json` after the checkpoint, so the restore removes the
   kernel's own scratch file too). `Rewind` is only enabled once the plan lands. After the restore
   the spec asserts `seed.txt` reads `before\n` byte for byte, `created.txt` is gone, the marker is
   present, no `message-user` is left, and a retried prompt reaches the provider as exactly
   `["system", "user"]` ending in the new text — no trace of the abandoned turn.
2. **The refusal.** An `ntool` prompt parks the turn on its permission card, so the workspace stays
   mid-turn without a clock in the test. `Rewind` reports `A turn is running in this workspace` and
   nothing moves: after the dialog is cancelled and the tool allowed, the prompt is still in the
   transcript and there is no marker.

## 11. Non-goals

- Per-file or per-hunk selective rewind.
- Rewind across workspaces or across sessions.
- Forward/redo.
- Truncating an ACP/OMP engine's own session file.
- Browsing snapshots, diffing two checkpoints, or a retention UI beyond `git gc`.
- Snapshotting while no turn is running (idle drift is the user's own doing, and the safety
  checkpoint at restore time covers it).

## 12. Recorded trade-offs

- **Storage is unbounded until git prunes.** Objects are deduped, so repeated snapshots of an
  unchanged repo cost a tree and a commit each. A cap or a prune policy is deferred, not forgotten;
  the disk check in §3 keeps the failure mode "stop snapshotting", never "fill the disk".
- **A snapshot is a git snapshot.** `.gitattributes` filters apply as git applies them, so a workspace
  whose attributes rewrite content (LFS, `ident`, `eol`) is treated by git's rules rather than by ours.
  Only LFS is detected and refused, because it is the one that silently corrupts.
- **The abandoned turns remain readable in the log.** That is deliberate (ADR-0002) and is what makes
  "Load the prompt again" possible without a separate store.
