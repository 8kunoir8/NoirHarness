# M4.3 — The LAN listener speaks TLS

Status: design. Closes the one weakness M4.2 documented instead of fixing: the device cookie
crossed the network in cleartext.

## 1. Intent

The paired browser loads `https://<machine>:<port>/`, the cookie is `Secure`, the socket is `wss://`,
and the only thing the user has to accept is a self-signed certificate — once, and verifiably,
because the pane shows the fingerprint the browser will complain about.

`http://` on that port is not served at all. There is no plaintext path to a session.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Where the key lives | `<dataDir>/tls/key.pem` + `cert.pem`, `0600`, generated on first `remote.enable` | It is kernel state, next to the database, not an app asset |
| Key type | ECDSA P-256, SHA-256 | `node:crypto` signs it directly; no RSA padding decisions, small files, fast handshakes |
| Generation | Hand-rolled DER, ~200 lines, zero dependencies | `node:crypto` can mint keys but not certificates, and `openssl` is not guaranteed on Windows |
| SANs | `DNS:localhost`, `IP:127.0.0.1`, `IP:::1`, every non-internal IPv4 | The browser connects by IP; a cert without it warns for the wrong reason |
| Validity | 5 years, `notBefore` 1 day back | Cheap reissue on address change; the clock skew allowance avoids `ERR_CERT_NOT_YET_VALID` |
| Plain HTTP | Not served | A downgrade path would undo the point of the milestone |
| `Origin`/`Host` guard | Scheme becomes `https` | The guard compares `Origin` to `<scheme>://<host>`; the scheme is now a parameter, not a constant |
| Cookie | `Secure` appended | Browsers refuse to send it over `http://`, which is exactly the desired failure |
| Fingerprint | SHA-256 over the DER, shown in the Devices pane | Verification without a CA: read it off the machine you trust |
| Trust on the client | Browser warning, accepted once | Installing a local CA is a bigger ask than a warning; it stays a non-goal |

## 3. The certificate

```
TBSCertificate
  version         v3 (explicit 2)
  serial          16 random bytes, positive
  signature       ecdsa-with-SHA256  1.2.840.10045.4.3.2
  issuer          CN=NoirHarness (<hostname>)
  validity        notBefore now-1d, notAfter now+5y (UTCTime)
  subject         CN=NoirHarness (<hostname>)
  spki            exported from the P-256 key, DER, untouched
  extensions [3]
    basicConstraints      critical, CA:FALSE
    keyUsage              critical, digitalSignature
    extKeyUsage           serverAuth
    subjectAltName        DNS:localhost, DNS:<hostname>, IP:127.0.0.1, IP:::1, IP:<each IPv4>
```

Signed with `crypto.sign("sha256", tbsDer, privateKey)` — the ECDSA output is already DER-encoded
`SEQUENCE { r, s }`, which is what the `signatureValue` BIT STRING wants.

`X509Certificate` (built into Node) parses the result in the test, so the encoder is checked against
a real parser, not against itself.

## 4. Reissue

The certificate is reused while it is still valid **and** its SAN list covers the current address set.
A laptop that moves between networks gets a new cert, and therefore a new fingerprint, on the next
`remote.enable` — the pane says when the fingerprint changed, because a device that trusted the old
one now sees a warning for a reason that is not an attack.

Deleting the two files is the supported reset.

## 5. Transport

- `remote.enable` binds `https` on `0.0.0.0:0`; `status()` reports `url: https://…` and `fingerprint`.
- `/pair/redeem` is served on the TLS listener (so the cookie is issued over TLS and carries
  `Secure`); the pairing URL is `https://<ip>:<port>/pair#<code>`.
- `/health` and `/shutdown` stay absent, as in M4.2.
- The loopback listener is untouched: still plain `http://127.0.0.1:<port>` with the runtime token.
  It never leaves the machine, and the Electron window has no opinion about certificates.

## 6. Client

`transport.ts` already picks `wss` when `location.protocol === "https:"`; the browser path needs no
change beyond that. Playwright needs `ignoreHTTPSErrors: true`, which is the same click a person
makes once in a browser.

## 7. Failure modes

| Situation | Behaviour |
|---|---|
| `tls/` unwritable | `enable()` rejects with `internal`; the toggle returns to off |
| Cert expired or SANs stale | Regenerated on the next enable; the pane names the new fingerprint |
| Device paired under the old cert | Browser warns again; the cookie is still valid once accepted — revocation is the only thing that ends a device |
| Two kernels, same data dir | Impossible: the lock file owns the directory |

## 8. Non-goals

A local CA or `mkcert` integration; client certificates; HSTS; OCSP/CRL; TLS on the loopback listener;
rotating the key on a schedule; encrypting the kernel database.

## 9. Testing

- **Unit (`tls.test.ts`)**: the generated cert parses; subject CN; `subjectAltName` contains every
  interface IPv4; `checkHost("127.0.0.1")` passes; signature verifies against its own public key;
  key file is `0600`; reissue when the SAN set changes; reuse when it does not.
- **Unit (`remoteAccess.test.ts`)**: the listener answers `https` and refuses a plain `http` request;
  a paired cookie carries `Secure`; the guard rejects an `http` `Origin` on an `https` request.
- **E2E (`remote.spec.ts`)**: unchanged except for `https://` and `ignoreHTTPSErrors`, which is the
  proof the browser path works end to end.
- The loopback suites must not move at all.
