# M4.0 Automation Design Specification

- Date: 2026-11-13
- Status: implemented — `e8f9664..` on `main`.
- Scope: the first half of M4 — scheduled agent runs inside the running app.

## 1. Intent

The base design defers one line: "Direction after M1: … M4 automation + remote runtime," and it
already committed to the shape automation needs — "Every action exists as a kernel RPC first; UI and
future automation share it." Today every run is started by a person pressing a button. What is
missing is a run that starts because it is due.

Success: a user creates a schedule in the Automations pane naming a workspace, an agent, a prompt,
and a cadence. At each due time the app starts a session and prompts it, without anyone present.
The run appears in Chats like any other session, its approvals land in Needs you, and its outcome is
readable in the schedule's run history. A fire that could not happen is recorded as missed or
skipped, never invented or silently retried.

Non-goals:

- **No daemon.** Schedules fire only while the app is open. The kernel is spawned by Electron main
  and dies with it (base design §3); making it survive a quit is a service install and a persistent
  trust surface, which belongs with remote runtime, not here.
- **No filesystem or git triggers.** No watcher exists in the kernel today. A watcher needs debounce,
  path filtering, and its own failure modes; a timer needs a clock.
- **No cron expression parser.** Cadence is an interval plus an anchor, which expresses every
  schedule the UI offers without a new grammar and its error surface.
- **No retries and no queue.** A failed fire records the failure and advances. A retry loop against a
  permanently broken target is a spinner; the record is the signal.
- **No continuing session per schedule.** Every fire is a fresh session.
- **No unattended auto-approval.** A run that needs a decision pauses.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| What a run is | An ordinary session with `schedule_id` set | History, events, approvals, the inspector, and Needs you all work unchanged. A parallel run type would duplicate every one of them |
| Lifecycle | In-app only | The kernel is a child of Electron main; a daemon is M4.1's problem and its security model |
| Trigger kinds | Time only | The only kind that is both cheap and exhaustively testable with an injected clock |
| Cadence model | `interval_minutes` + anchor | One field per user-facing schedule; no parser |
| Session per fire | Fresh | A continuing session grows context without bound and lets one bad turn poison every later run |
| Overlapping fire | Skipped and recorded | A backlog spends money on runs that are already stale |
| Unattended approval | Pause; the run goes `waiting` | Truthful: nothing happens unwatched, and `write-outside-workspace` is forced to `ask` regardless of policy anyway |
| Missed runs | Advanced past, recorded as `missed` | App-closed and laptop-asleep are the same case. Executing a 12-hour-late run is a surprise, not a service |
| Run history | `schedule_runs` table, cursor-paginated | It grows without bound, so it never rides on `schedule.list` |
| Clock and timer | Injected | A daily cadence must be testable in microseconds, not by sleeping |

## 3. Data model

Migration `9`. Two additions.

```sql
CREATE TABLE schedules (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  agent_id TEXT NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  prompt TEXT NOT NULL,
  interval_minutes INTEGER NOT NULL,
  anchor_minutes INTEGER NOT NULL DEFAULT 0,   -- minutes past local midnight for the first run
  enabled INTEGER NOT NULL DEFAULT 1,
  next_run_at INTEGER NOT NULL,
  last_run_at INTEGER,
  created_at INTEGER NOT NULL,
  UNIQUE (workspace_id, name)
);

CREATE TABLE schedule_runs (
  id TEXT PRIMARY KEY,
  schedule_id TEXT NOT NULL REFERENCES schedules(id) ON DELETE CASCADE,
  status TEXT NOT NULL,        -- 'fired' | 'skipped' | 'missed' | 'failed'
  due_at INTEGER NOT NULL,
  started_at INTEGER NOT NULL,
  session_id TEXT REFERENCES sessions(id) ON DELETE SET NULL,
  reason TEXT
);
CREATE INDEX schedule_runs_lookup ON schedule_runs (schedule_id, due_at DESC);

ALTER TABLE sessions ADD COLUMN schedule_id TEXT REFERENCES schedules(id) ON DELETE SET NULL;
```

`ON DELETE SET NULL` on `sessions.schedule_id` and `schedule_runs.session_id`: deleting a schedule
must not delete the sessions it ran, and deleting a session must not erase the record that the run
happened. `ON DELETE CASCADE` on `schedule_runs.schedule_id`: the run history belongs to the
schedule and has no meaning without it.

`next_run_at` and `last_run_at` are stored rather than derived, because a skipped fire still
advances the clock — a derived value could not express "due, but not run."

The anchor is minutes past **local** midnight. "Daily at 09:00" is `interval_minutes = 1440`,
`anchor_minutes = 540`. "Every 15 minutes" is `interval_minutes = 15`, anchor `0` — the run lands on
the quarter hour; the same interval with anchor `7` lands on :07, :22, :37, :52, and anchor `15`
with `interval_minutes = 60` is "hourly at :15".

The chain starts at `anchorMinutes` past local midnight on the day the schedule was created, then
walks forward until it is future. A schedule created at 10:07 with a 00 anchor and a 15-minute
interval therefore first runs at 10:15, not immediately — the anchor lines the cadence up, it does
not mean "right now".

**One function computes every `next_run_at`**, on create, on update, and on every advance. It is a
chain, not a closed form: the next occurrence is one interval after the *previous scheduled
occurrence*, and the step is taken in local wall-clock minutes, never by adding milliseconds.

```
advance(at, intervalMinutes) =
  add intervalMinutes to the local wall-clock fields of `at`,
  carrying whole days at local midnight
```

For `intervalMinutes = 1440` and a 09:00 schedule, `advance` returns 09:00 on the following local
day. Adding `86_400_000` instead would land at 08:00 or 10:00 after a DST boundary; reconstructing
the instant from local fields is what avoids that. A schedule whose stored `next_run_at` is already
past is walked forward with repeated `advance` until it is future — the same operation create,
update, and catch-up all need.

The older closed form this replaces was wrong: requiring `t - anchorAt(D)` to be a multiple of
`intervalMinutes` is vacuous once `t` is defined as `anchorAt(D)`, so every local day would have
qualified and a weekly cadence could not be expressed at all. The chain has no such ambiguity.

The walk is bounded. Past `MAX_ADVANCE_STEPS` (5000) steps the schedule re-aligns to the first
*anchored* occurrence after `now` and says so in the `missed` row's `reason`; a 1-minute schedule left
closed for a year would otherwise spend a million `Date` constructions on startup to produce a number
nobody reads. Anchoring the re-alignment is what keeps a 15-minute cadence on the quarter hour
instead of landing one interval after whenever the app happened to be opened.

## 4. The scheduler

`packages/kernel/src/scheduler.ts`, constructed in `startKernel` beside `engineManager` and stopped
from `kernel.close()` before `engines.shutdown()`.

**One armed timer.** At most one `setTimeout` points at the earliest `next_run_at` across enabled
schedules; it is re-armed after every tick from the clock, never by `setInterval`, which drifts and
can fire into a running tick. The timer is `unref()`'d so a kernel with nothing to do can still exit.
Every write through RPC — create, update, delete — calls `reschedule()`, because a timer armed before
a schedule existed is aimed past it, or absent when nothing was enabled at startup.

The armed delay is clamped to `[1_000, 2^31-1]` ms. The upper bound is not decoration: `setTimeout`
stores its delay in 32 bits and silently clamps anything larger to 1 ms, so a schedule more than
~24.8 days out would otherwise spin the event loop. The lower bound throttles a row that is stuck in
the past, which is what a fire that threw before recording itself leaves behind.

**Injection.** `Scheduler({ now, setTimer, clearTimer, createSession, prompt, slackMs })`. Tests pass
a fake clock and call `tick()` directly. `createSession` is the seam that lets a test assert the fire
without starting an engine.

**A tick, per due schedule:**

1. Inside one transaction: classify the fire (`fired` / `skipped` / `missed` / `failed`), insert the
   `schedule_runs` row, advance `next_run_at` past `now`, and set `last_run_at`. Advancing first is
   what makes a crash mid-tick unable to double-fire.
2. Outside the transaction, only for `fired`: create the session, set the run's `session_id`, and
   prompt it. A crash between the two leaves a `fired` row with no `session_id`, which reads as
   "started and died" and never as a second fire.

The row exists before the session does, so `schedule_runs.session_id` must be nullable and
`ScheduleRunView.sessionId` is `string | null`. `schedule.runNow` returns the row it inserted after
step 2, so its `sessionId` is non-null on success; a `runNow` that fails at step 2 returns the
`failed` row instead of throwing, because the record is the outcome.

**Catch-up.** A schedule that is more than `SLACK_MS` (60 s) past due records one `missed` row whose
`reason` carries how many occurrences were skipped, then advances to the next future occurrence. The
60 s slack matters: a tick that lands 20 ms after the due instant must fire, not count itself as
late. Startup and every tick share this path, so app-closed and asleep are one case.

Once past the slack, nothing fires on catch-up. A schedule two days late records one `missed` and
waits for its next real occurrence; it does not run two days of history at once.

**Overlap.** If the newest `fired` run's session is `starting`, `running`, or `waiting`, the fire
records `skipped` with reason `"the previous run was still working"` and the clock still advances.
The probe reads the newest *fired* run, not the newest row: once a skip is recorded on top, the
newest row is the skip, and reading it would report a still-working session as free and start a
second one.

**Failure.** A fire that cannot create its session — workspace deleted, agent archived — records
`failed` with the reason, advances, and stays enabled. The user fixes the cause and the schedule
resumes on its next occurrence. A prompt that rejects before a turn exists marks its run `failed`
too, so the history explains an empty chat instead of reading "fired".

Each due schedule is fired inside its own guard: one row that throws while recording cannot abort
the rest of the tick or escape the timer callback as an uncaught exception. The thrower's instant is
re-armed on the 1 s floor described above, so a broken row is retried slowly rather than spinning.

**Time at fire** is `now()`, not `due_at`; `due_at` keeps the scheduled instant for the record.

## 5. Protocol

`packages/protocol/src/schedules.ts`, re-exported from `index.ts`.

```ts
export const ScheduleStatus = z.enum(["fired", "skipped", "missed", "failed"]);

export const ScheduleView = z.object({
  id: z.string(),
  workspaceId: z.string(),
  agentId: z.string(),
  name: z.string(),
  prompt: z.string(),
  intervalMinutes: z.number().int().positive(),
  anchorMinutes: z.number().int().min(0).max(1439),
  enabled: z.boolean(),
  nextRunAt: z.number().int(),
  lastRunAt: z.number().int().nullable(),
  createdAt: z.number().int(),
  /** Derived: the newest run is `fired` and its session is still working. Never stored. */
  running: z.boolean(),
});

export const ScheduleRunView = z.object({
  id: z.string(),
  scheduleId: z.string(),
  status: ScheduleStatus,
  dueAt: z.number().int(),
  startedAt: z.number().int(),
  sessionId: z.string().nullable(),
  reason: z.string().nullable(),
});
```

`running` is derived. A stored flag would let a crash leave a schedule permanently "running" and
permanently skipping.

`SessionView` gains `scheduleId: z.string().nullable()`, so a run's origin survives into Chats. The
field is nullable and present everywhere, so every existing row and test stays valid.

Methods, mirroring the skill surface's shape:

| Method | Params | Returns |
|---|---|---|
| `schedule.list` | `workspaceId?` | `{ schedules: ScheduleView[] }`, ordered by `name` |
| `schedule.create` | `workspaceId`, `agentId`, `name`, `prompt`, `intervalMinutes`, `anchorMinutes?`, `enabled?` | `ScheduleView` |
| `schedule.update` | `id`, plus any of `name`, `prompt`, `intervalMinutes`, `anchorMinutes`, `enabled` | `ScheduleView` |
| `schedule.delete` | `id` | `{ ok: true }` — run history cascades with the schedule; its sessions survive and stay in Chats |
| `schedule.runNow` | `id` | `{ run: ScheduleRunView }` — `run.status` is `fired` with a `sessionId`, or `failed` with a `reason` |
| `schedule.runs` | `id`, `limit?` (1–100, default 20), `before?` | `{ runs: ScheduleRunView[], nextBefore: number \| null }` |

`schedule.update` is a patch: an absent field is unchanged, and `workspaceId`/`agentId` are not
mutable — moving a schedule to another agent is a different schedule, and re-pointing one silently
would make its run history describe work another agent did. Changing `intervalMinutes` or
`anchorMinutes` recomputes `next_run_at` from now, so editing a cadence never triggers an immediate
catch-up fire.

`schedule.runs` pages on `due_at`, descending: `nextBefore` is the `dueAt` to pass back, and `null`
when the page is the last. The service reads one row past `limit` to answer that question, because a
page that is exactly full is otherwise indistinguishable from the last page. A cursor on `due_at`
alone is stable because two runs of one schedule cannot share a due instant — the advance
transaction guarantees it.

**Errors** follow the existing mapping: `invalidParams` for `intervalMinutes < 1` or an anchor
outside 0–1439, `notFound` for a missing schedule, agent, or workspace, `conflict` for a duplicate
name in a workspace, for an archived agent at create, and for `runNow` while the schedule is running.
A failure while *performing* the fire is not an RPC error: it returns the `failed` run row, because
the record is the answer and the caller needs it either way.

`runNow` bypasses the clock but not overlap: letting a user stack runs on a still-working session is
exactly what the skip rule exists to prevent.

## 6. Panel

A fifth rail item, `Automations`. The pane is scoped to the workspace selected in the app, exactly
like Skills, so the editor has no workspace picker: `schedule.create` always carries the pane's
workspace. List pane: schedule rows with name, agent, cadence, next run, and a status chip, each row
also carrying `Pause`/`Resume` (`schedule.update`) and `Run now`. Main pane: the editor (name, agent,
prompt, cadence as `every N minutes`, `hourly at :MM`, or `daily at HH:MM`) above the run history,
each row linking to its session. A whole-day cadence shows a `Time` field (the wall-clock run time);
a shorter one shows a `Minute` field — the phase the cadence is lined up on, `:00`–`:59` — which is
what makes "hourly at :15" expressible. The minute is the anchor modulo 60, so retiming a daily 09:00
schedule to hourly reads "at :00" rather than ":540 past the hour".

Saving an existing schedule sends only the fields that changed, because `schedule.update` requires at
least one field and the kernel re-aligns `next_run_at` on a cadence edit. A new schedule defaults to
daily at 09:00 and enabled; the row's `Pause` is how an existing one is switched off.

The open pane re-reads its rows and the selected schedule's history every 15 s. A fire is recorded
in the kernel with no event to announce it: `AgentEvent` requires a `sessionId`, `events.session_id`
is `NOT NULL`, and a schedule-level event would have to invent one or widen the envelope every
consumer already parses. The poll costs one `schedule.list` and one `schedule.runs` per 15 s while
the pane is visible, touches no protocol, and also picks up a fire the user did not cause — which is
the only case that matters, since a write already re-lists. The editor's draft is never refreshed.

Chats shows a `scheduled` tag on a session with `scheduleId`, and Needs you already surfaces a
paused run because it is an ordinary unanswered approval.

Automation is not folded into the Skills pane: a schedule names a workspace *and* an agent, while
Skills is per-workspace config. Different lifetimes, different panes.

## 7. Failure modes and how each reads

| Situation | Record | User sees |
|---|---|---|
| App closed across a due time | `missed` with count | History says runs were missed; nothing ran late |
| Previous run still working | `skipped` | History says why; no backlog |
| Workspace or agent gone | `failed` with reason | History names the cause; schedule stays enabled |
| Run paused on approval | run `fired`, session `waiting` | Needs you lists it; answering resumes the turn |
| Crash mid-tick | `fired`, `session_id` null | "Started and died"; the next occurrence fires normally |
| Schedule deleted | runs cascade, sessions survive | Chats keeps the transcripts |

## 8. Testing

- **Scheduler unit** (fake clock, `tick()` called directly): not due; due fires once; a second tick
  at the same instant does not fire again; catch-up records `missed`; overlap records `skipped` and
  still advances; a create failure records `failed` and keeps the schedule enabled; `stop()` after a
  tick leaves no armed timer; a turn that never resolves does not stop the next timer from arming.
- **Cadence arithmetic:** `advance` keeps a 09:00 daily schedule at 09:00 on the next local day and
  keeps a 15-minute cadence on the quarter hour across midnight; `nextAfter` returns `anchor` when
  it is still future, walks past it when it is not, and stops at `MAX_ADVANCE_STEPS` by re-aligning
  to one interval after `now` instead of walking further. The DST property is **reviewed, not
  tested**: it needs control of `TZ`, which Node applies only at process start, so a portable test
  would have to re-exec itself. The implementation avoids the bug by reconstructing instants from
  local calendar fields; any test that matters here would be pinning `TZ`.
- **RPC:** create → list → `runNow` → `runs` shows a `fired` row whose session carries the
  `scheduleId` → delete keeps the session and relaxes its `schedule_id` to null → a duplicate name is
  `conflict` and an unknown id is `notFound`. `runNow` while running is `conflict` is pinned by the
  scheduler unit test instead, where the session row can be made live directly.
- **Panel:** the list shows the cadence and the enabled state; creating sends the parsed `create`
  params and re-lists; `Run now` opens the returned session; `Pause` sends exactly `{ id, enabled }`;
  an open pane picks up a row that flipped to running on its own. An hourly schedule created on
  `:15` sends `anchorMinutes: 15` and reads back `hourly at :15`; retiming a daily 09:00 row to
  hourly sends `anchorMinutes: 0`, so a wall clock is never stored as a minute past the hour.
- **End to end** (`apps/desktop/test/automations.spec.ts`): a schedule created in the panel, retimed
  to one minute over the socket, fires from the real timer into a real session and a real engine,
  answers through the mock provider, and appears in the open pane without a remount. This is the only
  test that exercises the timer, the engine, and the poll together; every other scheduler test drives
  `tick()` against a fake clock.
